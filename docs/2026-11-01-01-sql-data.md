# 2026-11-01-01-sql-data.md

Also filed as issue #1: https://github.com/joeblew999/bathroom-renovation-mon/issues/1

## Plan: the data as SQL text, checked by SQLite

**Status:** plan only. No code changes until the owner says go.

## The idea in one paragraph

The data stays text in the repo, but the text is SQL. Each part has a **schema** file (its tables, their types, required columns, ids, links, and rules) and a **data** file (its rows, one `INSERT` per row). Every build loads them into an in-memory SQLite database. That database lasts for the run and is never saved or committed. SQLite enforces the schema, and the code reads its rows with queries. GitHub diffs the data line by line, as it does the TOML today.

## Facts checked on this machine (1 Nov 2026)

| Question | Answer |
|---|---|
| SQLite in our pinned Python 3.13.18 | 3.53.1. `STRICT` tables need 3.37 or later. |
| Wrong type | `cannot store TEXT value in REAL column product.price` (names table and column) |
| Missing required value | `NOT NULL constraint failed: product.th` |
| Duplicate id | `UNIQUE constraint failed: unit.id` |
| A rule named as a sentence | `CONSTRAINT "x can't be negative" CHECK (x >= 0)` → `CHECK constraint failed: x can't be negative` |
| A link to nothing | SQLite says only `FOREIGN KEY constraint failed`, so links are checked after loading with `PRAGMA foreign_key_check`, which returns `(table, rowid, parent table)` for every broken row |
| "A part belongs to an item on the **same** wall" | A composite foreign key `(wall, part) → wall_item(wall, id)` enforces it: the same id on another wall is refused |
| Cross-row rules | `CREATE VIEW check_… AS SELECT '<message>' …` lives in the schema; the loader runs every view named `check_%` |
| Splitting a data file into statements, keeping line numbers | `sqlite3.complete_statement()` handles `;` inside text correctly |

## Files

| Now | After |
|---|---|
| `materials.toml` | `materials.schema.sql`, `materials.data.sql` |
| `room.toml` | `room.schema.sql`, `room.data.sql` |
| `phases.toml` | `phases.schema.sql`, `phases.data.sql` |

That is six text files instead of three: one schema and one data file per part. The parts stay separate (rule 5). Table names start with their part (`materials_…`, `room_…`, `phases_…`), so nothing collides in the one database.

The one link between parts (rule 6) is declared in `room.schema.sql`. Room tables have foreign keys to `materials_product(id)`, so the room's schema is the only place that names another part. The load order is materials, then room, then phases.

## The schemas

Every table is `STRICT`. Row order is the order of the lines in the data file (rowid). Every query that cares about order uses `ORDER BY rowid`, so there are no typed position numbers (rule 7).

**materials.schema.sql**
- `materials_setting`: one row (`id = 1`). Holds `prices_date`, `date_format` and `round_approx`.
- `materials_section`: one row. `th`, `en`, `note_th`, `note_en`.
- `materials_label (key PK, th, en)` and `materials_symbol (key PK, value)`.
- `materials_shop (id PK, th, en, sku, link)` and `materials_unit (id PK, th, en, en_many)`.
- `materials_group (id PK, th, en, note_th, note_en)`.
- `materials_status (id PK, to_buy, paid, on_site, by)`. Its four fixed rows are written in the schema, not the data, because each status's behaviour is code.
- `materials_product`:
  - its columns: `id` (PK), `th`, `detail_th`, `en`, `detail_en`, `w`, `h`, `d`, `per_box`, `unit` (→ unit), `price`, `approx`, `shop` (→ shop), `sku`
  - row rules: `w`, `h` and `d` more than 0, `per_box` a whole number more than 0, a price that can't be negative, shop and sku together, and approx only with a price
- `materials_line`:
  - its columns: `product` (→ product), `grp` (→ group), `status` (→ status), `n`, `note_th`, `note_en`, `by_th`, `by_en`
  - row rules: `n` more than 0, and both languages or neither for each pair

**room.schema.sql**
- `room_room`: one row. `length`, `width`, `ceiling`, `min_clear`, all more than 0.
- `room_column`: one row. `th`, `en`, `note_th`, `note_en`, `width`, `wall` (→ wall).
- `room_door`: one row. `product` (→ materials_product), plus its note.
- `room_lintel`: one row. `product` (→ materials_product), `bearing`, plus its note.
- `room_tile (id PK, product UNIQUE → materials_product, th, en, top, fill)`. `top` is a whole number more than 0.
- `room_floor`: one row. `tag`, `tile` (→ tile).
- `room_wall (id PK, th, en, tag, tile → tile, drawn)`.
- `room_wall_item`:
  - its columns: `wall` (→ wall), `id`, `product` (→ materials_product), `th`, `en`, `shape`, `x`, `y`, `w`, `h`, `d`, `part`, `note_th`, `note_en`
  - its id is `(wall, id)`, and `(wall, part)` → `(wall, id)`
  - row rules:
    - a product or a name, one, not both
    - an item with a product types no size
    - only the keys its shape uses (one `CHECK` per shape)
    - the shape is one of the wall shapes
    - the id isn't `column`, `door` or `lintel`
- `room_floor_item`:
  - its columns: `id` (PK), `product`, `th`, `en`, `shape`, `x`, `y`, `w`, `h`, `d`, `high`
  - row rules: the same as wall items, for floor shapes, and `high` is in `('start', 'end')` for steps only
- `room_label`, `room_symbol`: as in materials.

**phases.schema.sql**
- `phases_section`, `phases_label`, `phases_symbol`.
- `phases_phase (id PK, th, en, note_th, note_en)`.
- `phases_step (id PK, phase → phase, th, en)`. A step id is unique across all phases.

## Where each of today's checks goes

Today's checks split three ways. Nothing is lost; every test idea carries over.

**1. Schema constraints (row by row, enforced by SQLite)**
- types, required values, unique ids, and links (every `@x` today)
- amount, count and whole numbers
- both languages or neither
- keys that come together
- one-row tables
- the keys each shape may have
- product or name
- the reserved ids
- unique tile products
- a part on the same wall

**2. Check views (rules across rows, in the schema)**
Each view returns one message per broken row. The message is SQL text in the schema, so the rule and its wording sit together.
- exactly four walls
- tags unique across the walls and the floor
- a wall with items must be drawn
- every product has at least one line
- the status rules: a price needed, allowed or not allowed; a shop needed or not; `by_*` needed or not
- the room's products have the sizes the room needs:
  - the door: w and h
  - the lintel: h
  - each tile: square, a whole number of mm, with tiles-per-box
- the door fits beside the column
- the lintel is at least the door plus its bearing
- every label the code uses is present, and no others

**3. Code (things SQL can't check)**
- `{…}` placeholders in text: product sizes, the section note, labels, and the fact that drawing notes fill in nothing
- phase references `{step:id}`, and stray braces
- each shop's `sku` regular expression
- the design rules, which are warnings, not errors (unchanged)

The checker (`common.check` with its type strings) and every field-declaration dict in the parts are removed.

## Errors stay one plain line naming the file (rule 8)

The loader runs each data file one statement at a time and remembers `table + rowid → file:line`. Then:
- **a constraint error** reads like `materials.data.sql line 412 (materials_product): CHECK constraint failed: price can't be negative`
- **after loading,** `PRAGMA foreign_key_check` turns each broken link into a line like `room.data.sql line 88 (room_wall_item): product 'no_such' is not in materials_product`
- **every `check_%` view** is run, and its first message is reported with the file of the table it is about

Rules are named as sentences, so the message is readable without a lookup table.

## How the data files look

There is one `INSERT` per row, naming its columns and leaving out the empty ones (as optional TOML keys are left out today):

```sql
INSERT INTO materials_product (id, th, detail_th, en, detail_en, w, h, d, unit, price, shop, sku)
  VALUES ('aac_block', 'อิฐมวลเบา TPI', '{w_cm} × {h_cm} × {d_cm} ซม.', 'TPI AAC block', '{w_cm} × {h_cm} × {d_cm} cm', 600, 200, 75, 'block', 26, 'homepro', '1110154');
```

Long Thai and English text is a normal quoted string; only a `'` is written twice. Comments (`-- …`) are allowed, so the data files keep their explanations. The field descriptions now in the TOML headers move into the schema files, next to the columns they describe, so each is written once.

## Editing

- **Primary:** edit the `.data.sql` text in any editor. Git shows exactly what changed.
- **Optional, for browsing or bulk edits:**
  - `mise run db` writes the database to `out/quote.db`. `out/` is never committed.
  - `mise run dump` writes it back to the `.data.sql` files, in table order then rowid order, with the same one-row-per-line layout.
  - A test checks that load-then-dump reproduces the files exactly, so a round trip changes only what was edited.
  - A new row added in a GUI lands at the end of its table. Rows that need a place in the order are moved in the text.
- **GUI choice: none is pinned in the repo.**
  - Datasette's editing plugin is still alpha (`datasette-write-ui` 0.0.1a14, which needs a Datasette 1.0 alpha; the latest stable Datasette is 0.65.5).
  - DB Browser for SQLite (3.13.1) is a desktop app that mise can't pin.
  - Anyone who wants one installs it themselves; the repo needs only `mise`.

## The code after

- **`common.py`:**
  - `load(db, schema, data)`: statement by statement, with line tracking
  - `checks(db)`: foreign keys and `check_%` views
  - `placeholders`
  - `Labels` read from a label table
  - headings and notes as now
- **Each part:** `load(db)` queries its own tables (`ORDER BY rowid`) into the same dataclasses as today. Rendering and the design rules are unchanged.
- **`build.py`:** opens `:memory:`, loads the six files in order, runs the checks, then the parts, then as now.
- **Expected size:** about 150 lines of Python go (the checker, the field dicts, the hand checks), and about 300 lines of SQL schema arrive. The schema replaces the TOML header comments as the one description of the data.

## The tests after

- The harness loads the real six files into a fresh in-memory database, applies one edit as SQL (`UPDATE`, `INSERT` or `DELETE` on a row found by what it is), then runs `assemble(db)`. There are no temp folders and no TOML writer.
- The finders query rows by what they are, not by position (rule 9).
- The 25 checker tests become tests that break a row: a wrong type, a missing value, a link to nothing, a duplicate id, each named rule, and each check view. They expect the rule's own name, read from the schema.
- The design-rule and behaviour tests keep their ideas and their expectations. Only their edit line changes.
- New tests:
  - load-then-dump reproduces the files
  - an error names the right file and line
  - `sqlite_version` is at least 3.37

## Migration, in one change

1. Write the three schema files.
2. Generate the three data files from the current TOML by script, with no retyping, then delete the TOML.
3. Change `common.py`, the three parts, `build.py` and `test_pipeline.py`.
4. Update the README (Files, How it's built, rules 2, 3 and 5–8) and the mise tasks (`db`, `dump`). No new package is needed, because `sqlite3` comes with Python.
5. **Prove it:**
   - the page and the PDF are byte-identical to today's (the data and the behaviour are unchanged)
   - lint and tests clean, 0 warnings
   - each check proven to fail when broken
   - the GitHub build green
   - an independent review

## What this does not solve

A room item pointing at a real but wrong product (the door at the basin) still builds, because a foreign key only proves that the product exists. Closing that gap needs a `kind` column on products and the kind each room slot expects. It is possible as a follow-up, in either format.
