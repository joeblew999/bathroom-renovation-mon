# 2026-11-01-01-sql-data.md

Plan: the data as SQL text, checked by SQLite. Also filed as issue #1:
https://github.com/joeblew999/bathroom-renovation-mon/issues/1

**Status:** decided, not started. No code has changed yet.

## The idea in one paragraph

The data stays text in the repo, but the text is SQL. Each part has a **schema** file (its tables, their types, required columns, ids, links and rules) and a **data** file (its rows, one `INSERT` per row). Every build loads them into an in-memory SQLite database. That database lasts for the run and is never saved or committed. SQLite enforces the schema, and the code reads its rows with queries. GitHub diffs the data line by line, as it does the TOML today.

## Decisions made, and why

1. **Text is the source, never a database file.** A `.db` file is binary: GitHub can't show what changed and edits can't be merged. The database is built from the text on every run.
2. **SQL text is what gets edited.**
   - Each row is one line that names its columns, so it reads almost like the TOML.
   - Comments (`-- …`) are allowed.
   - The cost is that long Thai and English prose sits inside quotes. That is accepted: the files are mostly edited by Claude, and the owner reads the PDF.
3. **One schema file and one data file per part** (materials, room, phases). The parts stay separate (rule 5). The room's schema is the only place that names another part, which is the one link (rule 6).
4. **Each rule has one home:**
   - Rules about one row are schema constraints.
   - Rules across rows are `check_…` views in the schema, each with its own message.
   - Only what SQL can't express stays in code.
5. **Rules are named as sentences,** so SQLite's own error reads plainly. Broken links are found right after loading and traced to their file and line (rule 8).
6. **Order is the line order in the data file** (rowid). No position numbers are typed (rule 7).
7. **No editing GUI is pinned.**
   - Datasette's editing plugin is still alpha.
   - DB Browser for SQLite can't be pinned by mise.
   - The repo needs only mise, and SQLite comes with Python.
   - Writing a database out for browsing, and dumping it back, is optional.
8. **Every product gets a `kind`,** and the room says which kind each of its slots expects. This closes the last gap: a room slot pointing at a real but wrong product (the door at the basin) now stops the build. It is added in this change because the same tables are being written anyway.
9. **The four statuses become a small fixed table in the schema,** so the status rules can be SQL views. What each status does stays in code.
10. **One migration, in one change,** with proof: the page and the PDF byte-identical to today's, every check shown to fail when broken, the GitHub build green, and an independent review.

## Facts checked on this machine (1 Nov 2026)

| Question | Answer |
|---|---|
| SQLite in our pinned Python 3.13.18 | 3.53.1. `STRICT` tables need 3.37 or later. |
| Wrong type | `cannot store TEXT value in REAL column materials_product.price` (names table and column) |
| Missing required value | `NOT NULL constraint failed: materials_product.th` |
| Duplicate id | `UNIQUE constraint failed: materials_unit.id` |
| A rule named as a sentence | `CONSTRAINT "a price can't be negative" CHECK (price >= 0)` → `CHECK constraint failed: a price can't be negative` |
| A link to nothing | SQLite says only `FOREIGN KEY constraint failed`. `PRAGMA foreign_key_check` returns `(table, rowid, parent table)` for every broken row, so links are checked after loading. |
| "A part belongs to an item on the same wall" | A composite foreign key `(wall, part) → room_wall_item(wall, id)` enforces it |
| Rules across rows | `CREATE VIEW check_… AS SELECT '<message>' …`; the loader runs every view named `check_%` |
| Splitting a data file into statements, keeping line numbers | `sqlite3.complete_statement()` handles `;` inside text correctly |

## From the TOML to SQL: a one-to-one mapping

| In the TOML | In SQL |
|---|---|
| a list of tables (`[[entry]]`, `[[wall]]`, `[[phase]]` …) | a table, one row each |
| a list inside an entry (a product's lines, a phase's steps, a wall's items) | its own table with a column pointing at its parent |
| a single table (`[room]`, `[door]`, `[lintel]`, `[section]`, `[floor]`) | a one-row table (`id INTEGER PRIMARY KEY CHECK (id = 1)`) |
| `[labels]`, `[symbols]` | a `…_label (key, th, en)` and a `…_symbol (key, value)` table per part |
| a product's `size = { w, h, d }` | three columns `w`, `h`, `d` |
| a top-level value (`prices_date`, `round_approx` …) | a column of a one-row settings table |
| the field dicts in the code (`ENTRY = {"id": "text!", …}`) | the column definitions |
| `"!"` required | `NOT NULL` |
| `"text"`, `"number"`, `"flag"`, `"date"` | `TEXT`, `REAL` / `INTEGER`, `INTEGER CHECK (… IN (0, 1))`, `TEXT CHECK (date(…) = …)`, in `STRICT` tables |
| `"amount"`, `"count"`, `"whole"` | `CHECK (… >= 0)`, `CHECK (… > 0)`, `INTEGER CHECK (… > 0)` |
| `"@unit"` and other links | `REFERENCES materials_unit(id)` |
| `"+sku"` keys that come together | `CHECK ((shop IS NULL) = (sku IS NULL))` |
| both languages or neither | `CHECK ((note_th IS NULL) = (note_en IS NULL))` |
| ids used once (`check_each`) | `PRIMARY KEY` / `UNIQUE` |
| keys in the declared order | nothing to check: a table's columns are fixed |
| the hand checks in Python (status rules, four walls, tags, the room's sizes …) | `check_…` views |

The data is the same. The rules are the same, written in one standard place instead of spread across Python dicts and hand checks. The two additions are `kind` and the statuses table.

## The schemas

These are the planned schema files, condensed (comments trimmed). In the real files, each column gets the explanation the TOML headers carry today.

**materials.schema.sql**
```sql
CREATE TABLE materials_setting (
  id           INTEGER PRIMARY KEY CHECK (id = 1),
  prices_date  TEXT NOT NULL CONSTRAINT "prices_date is a date" CHECK (date(prices_date) = prices_date),
  date_format  TEXT NOT NULL,
  round_approx INTEGER NOT NULL CONSTRAINT "round_approx is more than 0" CHECK (round_approx > 0)
) STRICT;

CREATE TABLE materials_section (
  id INTEGER PRIMARY KEY CHECK (id = 1),
  th TEXT NOT NULL, en TEXT NOT NULL, note_th TEXT, note_en TEXT,
  CONSTRAINT "a note in both languages, or neither" CHECK ((note_th IS NULL) = (note_en IS NULL))
) STRICT;

CREATE TABLE materials_label  (key TEXT PRIMARY KEY, th TEXT NOT NULL, en TEXT NOT NULL) STRICT;
CREATE TABLE materials_symbol (key TEXT PRIMARY KEY, value TEXT NOT NULL) STRICT;

CREATE TABLE materials_shop  (id TEXT PRIMARY KEY, th TEXT NOT NULL, en TEXT NOT NULL,
                              sku TEXT NOT NULL, link TEXT NOT NULL) STRICT;
CREATE TABLE materials_unit  (id TEXT PRIMARY KEY, th TEXT NOT NULL, en TEXT NOT NULL, en_many TEXT NOT NULL) STRICT;
CREATE TABLE materials_group (id TEXT PRIMARY KEY, th TEXT NOT NULL, en TEXT NOT NULL, note_th TEXT, note_en TEXT,
  CONSTRAINT "a note in both languages, or neither" CHECK ((note_th IS NULL) = (note_en IS NULL))) STRICT;
CREATE TABLE materials_kind  (id TEXT PRIMARY KEY) STRICT;   -- what a product is: door_frame, lintel, tile, lamp …

-- the four statuses: fixed, because each has its own behaviour in code
CREATE TABLE materials_status (id TEXT PRIMARY KEY, to_buy INTEGER NOT NULL, paid INTEGER NOT NULL,
                               on_site INTEGER NOT NULL, by_trade INTEGER NOT NULL) STRICT;
INSERT INTO materials_status VALUES ('buy',1,0,0,0), ('bought',0,1,1,0), ('reused',0,0,1,0), ('supplied',0,0,0,1);

CREATE TABLE materials_product (
  id TEXT PRIMARY KEY,
  kind TEXT NOT NULL REFERENCES materials_kind(id),
  th TEXT NOT NULL, detail_th TEXT NOT NULL, en TEXT NOT NULL, detail_en TEXT NOT NULL,
  w REAL CONSTRAINT "w is more than 0" CHECK (w > 0),
  h REAL CONSTRAINT "h is more than 0" CHECK (h > 0),
  d REAL CONSTRAINT "d is more than 0" CHECK (d > 0),
  per_box INTEGER CONSTRAINT "per_box is more than 0" CHECK (per_box > 0),
  unit TEXT NOT NULL REFERENCES materials_unit(id),
  price REAL CONSTRAINT "a price can't be negative" CHECK (price >= 0),
  approx INTEGER CONSTRAINT "approx only with a price" CHECK (approx IS NULL OR price IS NOT NULL),
  shop TEXT REFERENCES materials_shop(id),
  sku TEXT,
  CONSTRAINT "a shop and its sku come together" CHECK ((shop IS NULL) = (sku IS NULL))
) STRICT;

CREATE TABLE materials_line (
  product TEXT NOT NULL REFERENCES materials_product(id),
  grp TEXT NOT NULL REFERENCES materials_group(id),
  status TEXT NOT NULL REFERENCES materials_status(id),
  n REAL NOT NULL CONSTRAINT "n is more than 0" CHECK (n > 0),
  note_th TEXT, note_en TEXT, by_th TEXT, by_en TEXT,
  CONSTRAINT "a note in both languages, or neither" CHECK ((note_th IS NULL) = (note_en IS NULL)),
  CONSTRAINT "who brings it, in both languages" CHECK ((by_th IS NULL) = (by_en IS NULL))
) STRICT;

-- rules across rows: each view returns one message per broken row
CREATE VIEW check_product_has_a_line AS
  SELECT 'product ' || id || ' has no line — it isn''t on the list' FROM materials_product
  WHERE id NOT IN (SELECT product FROM materials_line);
CREATE VIEW check_status_price AS
  SELECT 'product ' || p.id || ' is ' || s.id ||
         CASE WHEN s.to_buy AND p.price IS NULL THEN ', so it needs a price' ELSE ', so it has no price' END
  FROM materials_line l JOIN materials_product p ON p.id = l.product JOIN materials_status s ON s.id = l.status
  WHERE (s.to_buy AND p.price IS NULL) OR (NOT s.to_buy AND NOT s.paid AND p.price IS NOT NULL);
CREATE VIEW check_status_shop AS
  SELECT 'product ' || p.id || ' is ' || s.id ||
         CASE WHEN p.shop IS NULL THEN ', so it needs a shop and sku' ELSE ', so it has no shop and sku' END
  FROM materials_line l JOIN materials_product p ON p.id = l.product JOIN materials_status s ON s.id = l.status
  WHERE (s.to_buy OR s.paid) <> (p.shop IS NOT NULL);
CREATE VIEW check_status_by AS
  SELECT 'product ' || l.product || ' is ' || s.id ||
         CASE WHEN s.by_trade THEN ', so it needs by_th and by_en' ELSE ', so it has no by_th and by_en' END
  FROM materials_line l JOIN materials_status s ON s.id = l.status
  WHERE s.by_trade <> (l.by_th IS NOT NULL);
```

**room.schema.sql**
```sql
CREATE TABLE room_room (id INTEGER PRIMARY KEY CHECK (id = 1),
  length REAL NOT NULL CHECK (length > 0), width REAL NOT NULL CHECK (width > 0),
  ceiling REAL NOT NULL CHECK (ceiling > 0), min_clear REAL NOT NULL CHECK (min_clear > 0)) STRICT;

CREATE TABLE room_tile (id TEXT PRIMARY KEY,
  product TEXT NOT NULL UNIQUE REFERENCES materials_product(id),     -- the one link to another part
  th TEXT NOT NULL, en TEXT NOT NULL,
  top INTEGER NOT NULL CONSTRAINT "top is more than 0" CHECK (top > 0),
  fill TEXT NOT NULL) STRICT;

CREATE TABLE room_wall (id TEXT PRIMARY KEY, th TEXT NOT NULL, en TEXT NOT NULL,
  tag TEXT NOT NULL UNIQUE, tile TEXT NOT NULL REFERENCES room_tile(id),
  drawn INTEGER NOT NULL CHECK (drawn IN (0, 1))) STRICT;             -- row order = order round the room

CREATE TABLE room_floor (id INTEGER PRIMARY KEY CHECK (id = 1),
  tag TEXT NOT NULL, tile TEXT NOT NULL REFERENCES room_tile(id)) STRICT;

CREATE TABLE room_column (id INTEGER PRIMARY KEY CHECK (id = 1), th TEXT NOT NULL, en TEXT NOT NULL,
  note_th TEXT, note_en TEXT, width REAL NOT NULL CHECK (width > 0),
  wall TEXT NOT NULL REFERENCES room_wall(id),
  CHECK ((note_th IS NULL) = (note_en IS NULL))) STRICT;
CREATE TABLE room_door (id INTEGER PRIMARY KEY CHECK (id = 1),
  product TEXT NOT NULL REFERENCES materials_product(id), note_th TEXT, note_en TEXT,
  CHECK ((note_th IS NULL) = (note_en IS NULL))) STRICT;
CREATE TABLE room_lintel (id INTEGER PRIMARY KEY CHECK (id = 1),
  product TEXT NOT NULL REFERENCES materials_product(id),
  bearing REAL NOT NULL CHECK (bearing > 0), note_th TEXT, note_en TEXT,
  CHECK ((note_th IS NULL) = (note_en IS NULL))) STRICT;

CREATE TABLE room_wall_item (
  wall TEXT NOT NULL REFERENCES room_wall(id),
  id TEXT NOT NULL CONSTRAINT "column, door and lintel are worked out, so no item takes those ids"
                   CHECK (id NOT IN ('column', 'door', 'lintel')),
  product TEXT REFERENCES materials_product(id),
  th TEXT, en TEXT,
  shape TEXT NOT NULL CONSTRAINT "a wall item is a rect, circle, point, zone or opening"
                      CHECK (shape IN ('rect', 'circle', 'point', 'zone', 'opening')),
  x REAL NOT NULL CHECK (x >= 0), y REAL CHECK (y >= 0),
  w REAL CHECK (w > 0), h REAL CHECK (h > 0), d REAL CHECK (d > 0),
  part TEXT, note_th TEXT, note_en TEXT,
  PRIMARY KEY (wall, id),
  FOREIGN KEY (wall, part) REFERENCES room_wall_item(wall, id),      -- a part is on the same wall
  CONSTRAINT "a product or a name (th, en) — one, not both" CHECK ((product IS NULL) = (th IS NOT NULL)),
  CONSTRAINT "a name in both languages" CHECK ((th IS NULL) = (en IS NULL)),
  CONSTRAINT "an item with a product takes its size from it" CHECK (product IS NULL OR (w IS NULL AND h IS NULL AND d IS NULL)),
  CONSTRAINT "a point has no size" CHECK (shape <> 'point' OR (w IS NULL AND h IS NULL AND d IS NULL)),
  CONSTRAINT "a zone has no y or h" CHECK (shape <> 'zone' OR (y IS NULL AND h IS NULL)),
  CONSTRAINT "an opening has no depth" CHECK (shape <> 'opening' OR d IS NULL),
  CONSTRAINT "a note in both languages, or neither" CHECK ((note_th IS NULL) = (note_en IS NULL))
) STRICT;

CREATE TABLE room_floor_item (
  id TEXT PRIMARY KEY CHECK (id NOT IN ('column', 'door', 'lintel')),
  product TEXT REFERENCES materials_product(id), th TEXT, en TEXT,
  shape TEXT NOT NULL CONSTRAINT "a floor item is a rect or a step" CHECK (shape IN ('rect', 'step')),
  x REAL NOT NULL CHECK (x >= 0), y REAL CHECK (y >= 0),
  w REAL CHECK (w > 0), h REAL CHECK (h > 0), d REAL CHECK (d > 0),
  high TEXT CONSTRAINT "a step's high side is start or end, and only a step has one"
            CHECK ((shape = 'step') = (high IN ('start', 'end'))),
  note_th TEXT, note_en TEXT,
  CHECK ((product IS NULL) = (th IS NOT NULL)), CHECK ((th IS NULL) = (en IS NULL)),
  CHECK ((note_th IS NULL) = (note_en IS NULL))
) STRICT;

CREATE TABLE room_label  (key TEXT PRIMARY KEY, th TEXT NOT NULL, en TEXT NOT NULL) STRICT;
CREATE TABLE room_symbol (key TEXT PRIMARY KEY, value TEXT NOT NULL) STRICT;

-- rules across rows
CREATE VIEW check_four_walls AS
  SELECT (SELECT count(*) FROM room_wall) || ' walls — the room has 4' WHERE (SELECT count(*) FROM room_wall) <> 4;
CREATE VIEW check_tags_once AS
  SELECT 'tag ' || f.tag || ' is used by the floor and a wall' FROM room_floor f JOIN room_wall w ON w.tag = f.tag;
CREATE VIEW check_items_drawn AS
  SELECT 'wall ' || id || ' has items but isn''t drawn' FROM room_wall
  WHERE NOT drawn AND id IN (SELECT wall FROM room_wall_item);
CREATE VIEW check_product_kinds AS                                     -- the door at the basin can't build
  SELECT 'the door names ' || product || ', which is a ' || p.kind || ', not a door frame'
  FROM room_door JOIN materials_product p ON p.id = product WHERE p.kind <> 'door_frame'
  UNION ALL SELECT 'the lintel names ' || product || ', which isn''t a lintel'
  FROM room_lintel JOIN materials_product p ON p.id = product WHERE p.kind <> 'lintel'
  UNION ALL SELECT 'tile ' || t.id || ' names ' || t.product || ', which isn''t a tile'
  FROM room_tile t JOIN materials_product p ON p.id = t.product WHERE p.kind <> 'tile';
CREATE VIEW check_room_sizes AS
  SELECT 'tile ' || t.id || ' needs a square product, a whole number of mm, with per_box'
  FROM room_tile t JOIN materials_product p ON p.id = t.product
  WHERE p.w IS NULL OR p.w <> p.h OR p.w <> round(p.w) OR p.per_box IS NULL
  UNION ALL SELECT 'the door doesn''t fit beside the column'
  FROM room_door JOIN materials_product p ON p.id = room_door.product, room_column c, room_room r
  WHERE c.width + p.w >= r.width
  UNION ALL SELECT 'the lintel is shorter than the door and its bearing'
  FROM room_lintel l JOIN materials_product lp ON lp.id = l.product,
       room_door JOIN materials_product dp ON dp.id = room_door.product
  WHERE lp.w < dp.w + l.bearing;
```

## Product kinds

Every product gets a `kind`: the machine form of the kind word in its name (for example `aac_block`, `lintel`, `door_frame`, `door`, `tile`, `lamp`, `stop_valve`). The `materials_kind` table lists them, so a misspelt kind stops the build. Three room slots expect a kind:

| Room slot | Expects |
|---|---|
| `room_door.product` | `door_frame` (the opening is the frame's size) |
| `room_lintel.product` | `lintel` |
| `room_tile.product` | `tile` |

Wall and floor items may name any product, because they are drawn as what they are. The full list of kinds is settled during the migration, one per kind of product on the list.

## Where each of today's checks goes

Nothing is lost; every test idea carries over.

**1. Schema constraints (row by row, enforced by SQLite)**
- types, required values, unique ids, and links
- amount, count and whole numbers
- both languages or neither
- keys that come together
- one-row tables
- the keys each shape may have
- product or name
- reserved ids
- unique tile products
- a part on the same wall

**2. Check views (rules across rows, in the schema)**
- exactly four walls
- tags unique across the walls and the floor
- a wall with items must be drawn
- every product has a line
- the status rules (price, shop, `by_*`)
- the room's products are the right kind
- the room's products have the sizes it needs
- the door fits beside the column
- the lintel is at least the door plus its bearing
- every label the code uses is present, and no others

**3. Code (what SQL can't check)**
- `{…}` placeholders in text: product sizes, the section note, labels, and the fact that drawing notes fill in nothing
- phase references `{step:id}`, and stray braces
- each shop's `sku` regular expression
- the design-rule warnings (unchanged)

**Removed:** `common.check`, its type strings and every field-declaration dict in the parts. The "keys in the declared order" rule disappears, because a table's columns are fixed.

## Where the Thai and English live

Every word, in both languages, is in the three data files, Thai beside English in the same row:

| File | Text |
|---|---|
| `phases.data.sql` | phase names and notes, steps |
| `materials.data.sql` | product names and details, line notes, groups, units, shops, the section heading and note |
| `room.data.sql` | names and notes on the drawings, wall names, the column |
| each part's `…_label` table | the fixed wording: column headings, "buy", "approx.", the warning texts |

The code holds no wording.

**What is checked:**
- **Both languages present:** a schema constraint on every pair.
- **Each pair says the same facts:** a new test compares each Thai/English pair for:
  - the same `{…}` placeholders
  - the same numbers
  - the same codes and brand names (`HT-333`, `MOYA`, `IP44`, `H07` …)
  - the same step references

  It would have caught the past mismatches: a missing `{top}`, "40 cm" against "400 mm", and a count in one language only. This test can be added now on the TOML, and it carries over unchanged.
- **Whether the two mean the same:** a person, or an AI review, as now. No test can check that.

## Errors stay one plain line naming the file (rule 8)

The loader runs each data file one statement at a time and remembers `table + rowid → file:line`.
- **A constraint error:** `materials.data.sql line 412 (materials_product): CHECK constraint failed: a price can't be negative`.
- **After loading:** `PRAGMA foreign_key_check` turns each broken link into `room.data.sql line 88 (room_wall_item): product 'no_such' is not in materials_product`.
- **Each `check_%` view** is run, and its first message is reported with the file of the table it is about.

## How the data files look

There is one `INSERT` per row, naming its columns and leaving out the empty ones (as optional TOML keys are left out today):

```sql
INSERT INTO materials_product (id, kind, th, detail_th, en, detail_en, w, h, d, unit, price, shop, sku)
  VALUES ('aac_block', 'aac_block', 'อิฐมวลเบา TPI', '{w_cm} × {h_cm} × {d_cm} ซม.', 'TPI AAC block',
          '{w_cm} × {h_cm} × {d_cm} cm', 600, 200, 75, 'block', 26, 'homepro', '1110154');
```

Only a `'` is written twice. The data files keep short `--` comments where they help. The field descriptions now in the TOML headers move into the schema files, next to their columns.

## Editing

- **Primary:** edit the `.data.sql` text.
- **Optional:**
  - `mise run db` writes the database to `out/quote.db`. `out/` is never committed.
  - `mise run dump` writes it back to the `.data.sql` files, in table order then rowid order, in the same layout.
  - A test proves that load-then-dump reproduces the files exactly.
  - A row added in a GUI lands at the end of its table; rows that need a place in the order are moved in the text.
- **No GUI is pinned** (decision 7). As checked on 1 Nov 2026:
  - Datasette's editing plugin `datasette-write-ui` is 0.0.1a14 and needs a Datasette 1.0 alpha; the latest stable Datasette is 0.65.5.
  - DB Browser for SQLite is 3.13.1.

## The code after

- **`common.py`:**
  - `load(db, schema, data)`: statement by statement, with line tracking
  - `checks(db)`: foreign keys and `check_%` views
  - `placeholders`
  - `Labels` read from a label table
  - headings and notes as now
- **Each part:** `load(db)` queries its own tables (`ORDER BY rowid`) into the same dataclasses as today. Rendering and the design rules are unchanged.
- **`build.py`:** opens `:memory:`, loads the six files in order, runs the checks, then the parts, then writes the page and the PDF as now.
- **Expected size:** about 150 lines of Python go, and about 300 lines of SQL schema arrive. The schema replaces the TOML header comments as the one description of the data.

## The tests after

- **The harness:** loads the real six files into a fresh in-memory database, applies one edit as SQL (`UPDATE` / `INSERT` / `DELETE` on a row found by what it is), then runs `assemble(db)`. There are no temp folders and no TOML writer.
- **Finders:** query rows by what they are, never by position (rule 9).
- **The checker tests:** each breaks a row (a wrong type, a missing value, a link to nothing, a duplicate id, each named rule, each check view) and expects the rule's own name, read from the schema.
- **The design-rule and behaviour tests:** keep their ideas and expectations; only their edit line changes.
- **New tests:**
  - load-then-dump reproduces the files
  - an error names the right file and line
  - `sqlite_version` is at least 3.37
  - each room slot refuses a product of the wrong kind
  - the Thai/English facts comparison

## Migration, in one change

1. Write the three schema files, with each column's explanation.
2. Generate the three data files from the current TOML by script (no retyping), adding each product's `kind`. Then delete the TOML.
3. Change `common.py`, the three parts, `build.py` and `test_pipeline.py`.
4. Update the README (Files, How it's built, rules 2, 3 and 5–8) and the mise tasks (`db`, `dump`). No new package is needed.
5. **Prove it:**
   - the page and the PDF byte-identical to today's
   - lint and tests clean, 0 warnings
   - each check shown to fail when broken
   - the GitHub build green
   - an independent review
