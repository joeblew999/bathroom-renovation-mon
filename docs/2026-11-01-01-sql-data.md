# 2026-11-01-01-sql-data.md

Plan: the data as SQL text, checked by SQLite. Also filed as issue #1:
https://github.com/joeblew999/bathroom-renovation-mon/issues/1

**Status:** decided, not started. No code has changed yet.

**Reviewed:** an independent review on 1 Nov 2026 found definite problems in the first version. This version fixes each of them; see "What the review changed" at the end. Every schema below was loaded into SQLite 3.53.1, and each rule was shown to refuse a bad row.

## The idea in one paragraph

The data stays text in the repo, but the text is SQL. Each part has a **schema** file (its tables, their types, required columns, ids, links and rules) and a **data** file (its rows, one `INSERT` per line). Every build loads them into an in-memory SQLite database. That database lasts for the run and is never saved or committed. SQLite enforces the schema, and the code reads its rows with queries. GitHub diffs the data line by line, as it does the TOML today.

## Decisions, and why

1. **Text is the source, never a database file.** A `.db` file is binary: GitHub can't show what changed and edits can't be merged.
2. **SQL text is what gets edited.**
   - Each row is one line that names its columns.
   - The cost is that long Thai and English prose sits inside quotes. That's accepted: the files are mostly edited by Claude, and the owner reads the PDF.
3. **One schema file and one data file per part** (materials, room, phases). The parts stay separate (rule 5).
4. **Each rule has one home:**
   - A rule about one row is a named constraint in the schema.
   - A rule across rows of one part is a `check_…` view in that part's schema.
   - What needs another part's data, the room's geometry, or text parsing stays in code.
   - A fact is never written in both the schema and the code (rule 7).
5. **Rules are named as sentences,** so SQLite's own error reads plainly. Every `CHECK` has a name.
6. **Every rule is written so a missing value fails it.** In SQL a check on a missing value counts as a pass, which let bad data through in the first version. Each rule is written for that:
   - a rule on an optional column starts `x IS NULL OR …`
   - "both or neither" uses `IS`, not `=`
   - a required value inside a rule is tested with `IS NOT NULL`
7. **Order is the line order in the data file** (rowid). No position numbers are typed (rule 7).
8. **The data files are one generated layout:** one `INSERT` per line, columns in the table's order, no comments.
   - `mise run dump` writes that layout, and a test proves every data file equals its own dump.
   - That test also replaces today's "keys in the declared order" check (rule 2).
   - What the TOML headers explain moves into the schema files, next to each column.
9. **No editing GUI is pinned.**
   - Datasette's editing plugin is still alpha.
   - DB Browser for SQLite can't be pinned by mise.
   - The repo needs only mise, and SQLite comes with Python.
10. **No product "kind" in this change.** The first version added one, so the room could insist the door names a door frame. The review showed the cost:
    - the room's schema would hold the material list's kind ids, a second link between parts (rules 5 and 6)
    - the kind would repeat the kind word already in each product's name (rule 7)

    The gap it closed, the room's door naming a real but wrong product, stays open. It's listed under "Not solved".
11. **The statuses (buy, bought, reused, supplied) become data:** a `materials_status` table in `materials.data.sql`.
    - It holds each status's flags (to buy, paid, on site, brought by the trade). Its line order is the order within a group.
    - The code reads the flags from that table instead of holding its own copy (today's `STATUS` dict goes).
12. **One migration, in one change,** proven as set out under "Migration".

## Facts checked on this machine (1 Nov 2026)

| Question | Answer |
|---|---|
| SQLite in our pinned Python 3.13.18 | 3.53.1. `STRICT` tables need 3.37 or later. |
| Wrong type | text in a number column: `cannot store TEXT value in REAL column room_room.ceiling`; `4.5` in a whole-number column: `cannot store REAL value in INTEGER column materials_product.per_box` |
| Converted quietly, not refused | `STRICT` turns `5` into the text `'5'` in a text column, and `'600'` into `600` in a number column. A `CHECK` can't see the original, so these two are accepted (see "What changes in the checks"). |
| Infinity | `1e999` is accepted unless a rule refuses it: each number rule includes `< 1e308`. NaN can't be written in SQL at all. |
| Missing required value | `NOT NULL constraint failed: materials_unit.en_many` |
| Unknown column (a typo) | `table materials_unit has no column named xx` |
| Duplicate id | `UNIQUE constraint failed: materials_unit.id` |
| A rule named as a sentence | `CHECK constraint failed: a price is 0 or more` |
| A link to nothing | SQLite says only `FOREIGN KEY constraint failed` if links are checked while loading. Instead, links are off while loading (SQLite's default) and checked after, with `PRAGMA foreign_key_check`. That returns `(table, rowid, parent table)` for every broken row, and a link may then point at a row loaded later. |
| "A part belongs to an item on the same wall" | a composite foreign key `(wall, part) → room_wall_item(wall, id)` refuses a part pointing at an item on another wall |
| Finding the check views | `name GLOB 'check_*'`. `LIKE` would treat `_` as any character and ignore case. |
| Splitting a data file into statements, keeping line numbers | `sqlite3.complete_statement()` handles `;` inside text correctly |
| PDF tools for the proof | `pdftotext` and `pdftoppm` are on this machine. The proof is a one-off check done here, not part of the build. |

## From the TOML to SQL

| In the TOML | In SQL |
|---|---|
| a list of tables (`[[entry]]`, `[[wall]]`, `[[phase]]` …) | a table, one row each |
| a list inside an entry (a product's lines, a phase's steps, a wall's items) | its own table with a column pointing at its parent |
| a single table (`[room]`, `[door]`, `[section]` …) | a one-row table: `id = 1`, plus a check that the row is there |
| `[labels]`, `[symbols]` | a `…_label (key, th, en)` and a `…_symbol (key, value)` table per part |
| a product's `size = { w, h, d }` | three columns `w`, `h`, `d` |
| top-level values (`prices_date` …) | a one-row `materials_setting` table |
| `"!"` required | `NOT NULL` |
| `"text"` | `TEXT` |
| `"number"`, `"amount"`, `"count"` | `REAL` with a named rule (`>= 0`, `> 0`, and always `< 1e308`) |
| `"whole"` | `INTEGER` with a named rule (`> 0`) |
| `"flag"` | `INTEGER` with a named rule (`IN (0, 1)`) |
| `"date"` | `TEXT` with `date(x) IS x` |
| `"@unit"` and other links | `REFERENCES materials_unit(id)` |
| `"+sku"` keys that come together | `(shop IS NULL) IS (sku IS NULL)` |
| ids used once | `PRIMARY KEY` / `UNIQUE` |

Numbers print as today: the code formats every number it prints with `:g`, so `20.0` prints as `20`. The one place that doesn't today, `min_clear` in the all-clear line (room.py `draw_warnings`), is fixed in the migration. The dump writes whole numbers without `.0`.

## The schemas

These are the planned schema files, loaded and tested in SQLite. The real files add each column's explanation from today's TOML headers.

**materials.schema.sql**
```sql
CREATE TABLE materials_setting (
  id           INTEGER PRIMARY KEY CONSTRAINT "settings is one row" CHECK (id = 1),
  prices_date  TEXT NOT NULL CONSTRAINT "prices_date is a date, YYYY-MM-DD" CHECK (date(prices_date) IS prices_date),
  date_format  TEXT NOT NULL,
  round_approx INTEGER NOT NULL CONSTRAINT "round_approx is more than 0" CHECK (round_approx > 0)
) STRICT;

CREATE TABLE materials_section (
  id INTEGER PRIMARY KEY CONSTRAINT "the section is one row" CHECK (id = 1),
  th TEXT NOT NULL, en TEXT NOT NULL, note_th TEXT, note_en TEXT,
  CONSTRAINT "a note in both languages, or neither" CHECK ((note_th IS NULL) IS (note_en IS NULL))
) STRICT;

CREATE TABLE materials_label  (key TEXT PRIMARY KEY, th TEXT NOT NULL, en TEXT NOT NULL) STRICT;
CREATE TABLE materials_symbol (key TEXT PRIMARY KEY, value TEXT NOT NULL) STRICT;

CREATE TABLE materials_shop  (id TEXT PRIMARY KEY, th TEXT NOT NULL, en TEXT NOT NULL,
                              sku TEXT NOT NULL, link TEXT NOT NULL) STRICT;
CREATE TABLE materials_unit  (id TEXT PRIMARY KEY, th TEXT NOT NULL, en TEXT NOT NULL, en_many TEXT NOT NULL) STRICT;
CREATE TABLE materials_group (id TEXT PRIMARY KEY, th TEXT NOT NULL, en TEXT NOT NULL, note_th TEXT, note_en TEXT,
  CONSTRAINT "a note in both languages, or neither" CHECK ((note_th IS NULL) IS (note_en IS NULL))
) STRICT;

CREATE TABLE materials_status (
  id       TEXT PRIMARY KEY,
  to_buy   INTEGER NOT NULL CONSTRAINT "to_buy is 0 or 1"   CHECK (to_buy IN (0, 1)),
  paid     INTEGER NOT NULL CONSTRAINT "paid is 0 or 1"     CHECK (paid IN (0, 1)),
  on_site  INTEGER NOT NULL CONSTRAINT "on_site is 0 or 1"  CHECK (on_site IN (0, 1)),
  by_trade INTEGER NOT NULL CONSTRAINT "by_trade is 0 or 1" CHECK (by_trade IN (0, 1))
) STRICT;

CREATE TABLE materials_product (
  id TEXT PRIMARY KEY,
  th TEXT NOT NULL, detail_th TEXT NOT NULL, en TEXT NOT NULL, detail_en TEXT NOT NULL,
  w REAL CONSTRAINT "w is more than 0" CHECK (w > 0 AND w < 1e308),
  h REAL CONSTRAINT "h is more than 0" CHECK (h > 0 AND h < 1e308),
  d REAL CONSTRAINT "d is more than 0" CHECK (d > 0 AND d < 1e308),
  per_box INTEGER CONSTRAINT "per_box is more than 0" CHECK (per_box > 0),
  unit TEXT NOT NULL REFERENCES materials_unit(id),
  price REAL CONSTRAINT "a price is 0 or more" CHECK (price >= 0 AND price < 1e308),
  approx INTEGER CONSTRAINT "approx is 1, and only with a price" CHECK (approx IS NULL OR (approx = 1 AND price IS NOT NULL)),
  shop TEXT REFERENCES materials_shop(id),
  sku TEXT,
  CONSTRAINT "a shop and its sku come together" CHECK ((shop IS NULL) IS (sku IS NULL))
) STRICT;

CREATE TABLE materials_line (
  product TEXT NOT NULL REFERENCES materials_product(id),
  grp     TEXT NOT NULL REFERENCES materials_group(id),
  status  TEXT NOT NULL REFERENCES materials_status(id),
  n REAL NOT NULL CONSTRAINT "n is more than 0" CHECK (n > 0 AND n < 1e308),
  note_th TEXT, note_en TEXT, by_th TEXT, by_en TEXT,
  CONSTRAINT "a note in both languages, or neither" CHECK ((note_th IS NULL) IS (note_en IS NULL)),
  CONSTRAINT "who brings it, in both languages, or neither" CHECK ((by_th IS NULL) IS (by_en IS NULL))
) STRICT;

CREATE VIEW check_materials_rows AS
  SELECT t || ' has no row' FROM (
    SELECT 'materials_setting' t, (SELECT count(*) FROM materials_setting) n UNION ALL
    SELECT 'materials_section', (SELECT count(*) FROM materials_section) UNION ALL
    SELECT 'materials_shop', (SELECT count(*) FROM materials_shop) UNION ALL
    SELECT 'materials_unit', (SELECT count(*) FROM materials_unit) UNION ALL
    SELECT 'materials_group', (SELECT count(*) FROM materials_group) UNION ALL
    SELECT 'materials_status', (SELECT count(*) FROM materials_status) UNION ALL
    SELECT 'materials_product', (SELECT count(*) FROM materials_product)) WHERE n = 0;
CREATE VIEW check_product_has_a_line AS
  SELECT 'product ' || id || ' has no line, so it isn''t on the list' FROM materials_product
  WHERE id NOT IN (SELECT product FROM materials_line);
CREATE VIEW check_status_price AS
  SELECT 'product ' || p.id || ' is ' || s.id ||
         CASE WHEN s.to_buy THEN ', so it needs a price' ELSE ', so it has no price' END
  FROM materials_line l JOIN materials_product p ON p.id = l.product JOIN materials_status s ON s.id = l.status
  WHERE (s.to_buy AND p.price IS NULL) OR (NOT s.to_buy AND NOT s.paid AND p.price IS NOT NULL);
CREATE VIEW check_status_shop AS
  SELECT 'product ' || p.id || ' is ' || s.id ||
         CASE WHEN p.shop IS NULL THEN ', so it needs a shop and sku' ELSE ', so it has no shop and sku' END
  FROM materials_line l JOIN materials_product p ON p.id = l.product JOIN materials_status s ON s.id = l.status
  WHERE (s.to_buy OR s.paid) IS NOT (p.shop IS NOT NULL);
CREATE VIEW check_status_by AS
  SELECT 'product ' || l.product || ' is ' || s.id ||
         CASE WHEN s.by_trade THEN ', so it needs by_th and by_en' ELSE ', so it has no by_th and by_en' END
  FROM materials_line l JOIN materials_status s ON s.id = l.status
  WHERE s.by_trade IS NOT (l.by_th IS NOT NULL);
```

**room.schema.sql**
```sql
CREATE TABLE room_room (
  id INTEGER PRIMARY KEY CONSTRAINT "the room is one row" CHECK (id = 1),
  length    REAL NOT NULL CONSTRAINT "length is more than 0"    CHECK (length > 0 AND length < 1e308),
  width     REAL NOT NULL CONSTRAINT "width is more than 0"     CHECK (width > 0 AND width < 1e308),
  ceiling   REAL NOT NULL CONSTRAINT "ceiling is more than 0"   CHECK (ceiling > 0 AND ceiling < 1e308),
  min_clear REAL NOT NULL CONSTRAINT "min_clear is more than 0" CHECK (min_clear > 0 AND min_clear < 1e308)
) STRICT;

CREATE TABLE room_tile (
  id TEXT PRIMARY KEY,
  product TEXT NOT NULL UNIQUE REFERENCES materials_product(id),
  th TEXT NOT NULL, en TEXT NOT NULL,
  top INTEGER NOT NULL CONSTRAINT "a tile's top is more than 0" CHECK (top > 0),
  fill TEXT NOT NULL
) STRICT;

CREATE TABLE room_wall (
  id TEXT PRIMARY KEY, th TEXT NOT NULL, en TEXT NOT NULL,
  tag TEXT NOT NULL UNIQUE,
  tile TEXT NOT NULL REFERENCES room_tile(id),
  drawn INTEGER NOT NULL CONSTRAINT "drawn is 0 or 1" CHECK (drawn IN (0, 1))
) STRICT;

CREATE TABLE room_floor (
  id INTEGER PRIMARY KEY CONSTRAINT "the floor is one row" CHECK (id = 1),
  tag TEXT NOT NULL, tile TEXT NOT NULL REFERENCES room_tile(id)
) STRICT;

CREATE TABLE room_column (
  id INTEGER PRIMARY KEY CONSTRAINT "the column is one row" CHECK (id = 1),
  th TEXT NOT NULL, en TEXT NOT NULL, note_th TEXT, note_en TEXT,
  width REAL NOT NULL CONSTRAINT "the column's width is more than 0" CHECK (width > 0 AND width < 1e308),
  wall TEXT NOT NULL REFERENCES room_wall(id),
  CONSTRAINT "a note in both languages, or neither" CHECK ((note_th IS NULL) IS (note_en IS NULL))
) STRICT;

CREATE TABLE room_door (
  id INTEGER PRIMARY KEY CONSTRAINT "the door is one row" CHECK (id = 1),
  product TEXT NOT NULL REFERENCES materials_product(id), note_th TEXT, note_en TEXT,
  CONSTRAINT "a note in both languages, or neither" CHECK ((note_th IS NULL) IS (note_en IS NULL))
) STRICT;

CREATE TABLE room_lintel (
  id INTEGER PRIMARY KEY CONSTRAINT "the lintel is one row" CHECK (id = 1),
  product TEXT NOT NULL REFERENCES materials_product(id),
  bearing REAL NOT NULL CONSTRAINT "the bearing is more than 0" CHECK (bearing > 0 AND bearing < 1e308),
  note_th TEXT, note_en TEXT,
  CONSTRAINT "a note in both languages, or neither" CHECK ((note_th IS NULL) IS (note_en IS NULL))
) STRICT;

CREATE TABLE room_wall_item (
  wall TEXT NOT NULL REFERENCES room_wall(id),
  id TEXT NOT NULL,
  product TEXT REFERENCES materials_product(id),
  th TEXT, en TEXT,
  shape TEXT NOT NULL CONSTRAINT "a wall item is a rect, circle, point, zone or opening"
                      CHECK (shape IN ('rect', 'circle', 'point', 'zone', 'opening')),
  x REAL NOT NULL CONSTRAINT "x is 0 or more" CHECK (x >= 0 AND x < 1e308),
  y REAL CONSTRAINT "y is 0 or more" CHECK (y >= 0 AND y < 1e308),
  w REAL CONSTRAINT "w is more than 0" CHECK (w > 0 AND w < 1e308),
  h REAL CONSTRAINT "h is more than 0" CHECK (h > 0 AND h < 1e308),
  d REAL CONSTRAINT "d is more than 0" CHECK (d > 0 AND d < 1e308),
  part TEXT, note_th TEXT, note_en TEXT,
  PRIMARY KEY (wall, id),
  FOREIGN KEY (wall, part) REFERENCES room_wall_item(wall, id),
  CONSTRAINT "a product or a name (th, en), one, not both" CHECK ((product IS NULL) IS (th IS NOT NULL)),
  CONSTRAINT "a name in both languages" CHECK ((th IS NULL) IS (en IS NULL)),
  CONSTRAINT "an item with a product takes its size from it" CHECK (product IS NULL OR (w IS NULL AND h IS NULL AND d IS NULL)),
  CONSTRAINT "a circle has no h" CHECK (shape IS NOT 'circle' OR h IS NULL),
  CONSTRAINT "a point has no w, h or d" CHECK (shape IS NOT 'point' OR (w IS NULL AND h IS NULL AND d IS NULL)),
  CONSTRAINT "a zone has no y or h" CHECK (shape IS NOT 'zone' OR (y IS NULL AND h IS NULL)),
  CONSTRAINT "an opening has no d" CHECK (shape IS NOT 'opening' OR d IS NULL),
  CONSTRAINT "a note in both languages, or neither" CHECK ((note_th IS NULL) IS (note_en IS NULL))
) STRICT;

CREATE TABLE room_floor_item (
  id TEXT PRIMARY KEY,
  product TEXT REFERENCES materials_product(id),
  th TEXT, en TEXT,
  shape TEXT NOT NULL CONSTRAINT "a floor item is a rect or a step" CHECK (shape IN ('rect', 'step')),
  x REAL NOT NULL CONSTRAINT "x is 0 or more" CHECK (x >= 0 AND x < 1e308),
  y REAL CONSTRAINT "y is 0 or more" CHECK (y >= 0 AND y < 1e308),
  w REAL CONSTRAINT "w is more than 0" CHECK (w > 0 AND w < 1e308),
  h REAL CONSTRAINT "h is more than 0" CHECK (h > 0 AND h < 1e308),
  d REAL CONSTRAINT "d is more than 0" CHECK (d > 0 AND d < 1e308),
  high TEXT,
  note_th TEXT, note_en TEXT,
  CONSTRAINT "a product or a name (th, en), one, not both" CHECK ((product IS NULL) IS (th IS NOT NULL)),
  CONSTRAINT "a name in both languages" CHECK ((th IS NULL) IS (en IS NULL)),
  CONSTRAINT "an item with a product takes its size from it" CHECK (product IS NULL OR (w IS NULL AND h IS NULL AND d IS NULL)),
  CONSTRAINT "a floor rect has no h or high" CHECK (shape IS NOT 'rect' OR (h IS NULL AND high IS NULL)),
  CONSTRAINT "a step has no y or w, and its high side is start or end"
             CHECK (shape IS NOT 'step' OR (y IS NULL AND w IS NULL AND high IS NOT NULL AND high IN ('start', 'end'))),
  CONSTRAINT "a note in both languages, or neither" CHECK ((note_th IS NULL) IS (note_en IS NULL))
) STRICT;

CREATE TABLE room_label  (key TEXT PRIMARY KEY, th TEXT NOT NULL, en TEXT NOT NULL) STRICT;
CREATE TABLE room_symbol (key TEXT PRIMARY KEY, value TEXT NOT NULL) STRICT;
```

## Where every check goes

Each of today's checks, by where it is now. Nothing is dropped without saying so.

**`common.check`: the checker (goes)**

| Today | After |
|---|---|
| file not found; not valid TOML | the loader: file not found; not valid SQL, with SQLite's message, file and line |
| unknown key (a typo) | SQLite: `has no column named …` |
| required key missing | `NOT NULL` |
| text where a number goes | `STRICT`: `cannot store TEXT value in REAL column …` |
| a number that isn't finite | each number rule's `< 1e308` |
| text where true/false goes | `STRICT` refuses text; the named `IN (0, 1)` rule refuses other numbers |
| a number where text goes | **accepted** (`5` becomes `'5'`), so this test goes. Nothing breaks: the value prints as written. |
| a value where a table or list goes | gone: SQL has no nesting |
| text where a date goes | `date(x) IS x` |
| a negative amount; a count not more than 0; a whole number | named rules and `INTEGER` |
| a name pointing at nothing | foreign keys, checked after loading |
| keys that come together; one language only | named rules using `IS` |
| an id used twice | `PRIMARY KEY` / `UNIQUE` |
| keys out of order | the round-trip test: every data file equals its own dump |
| a required list that's empty | each part's `check_…_rows` view; a product with no line: `check_product_has_a_line`. (A phase with no steps is allowed, as today.) |
| placeholders a text can't use; a stray brace | code, unchanged (`common.placeholders`) |

## Where the Thai and English live

Every word, in both languages, is in the three data files, Thai beside English in the same row:

| File | Text |
|---|---|
| `phases.data.sql` | phase names and notes, steps |
| `materials.data.sql` | product names and details, line notes, groups, units, shops, the section heading and note |
| `room.data.sql` | names and notes on the drawings, wall names, the column |
| each part's `…_label` table | the fixed wording: column headings, "buy", "approx.", the warning texts |

**What is checked:**
- **Both languages present:** `NOT NULL` and the named "both languages" rules.
- **Each pair says the same facts:** a new test checks every Thai/English pair for:
  - the same `{…}` placeholders
  - the same numbers

  Run on today's 299 pairs, placeholders differ in none, and numbers differ in one: the toilet, "1 ชิ้น" against "one-piece". That's fixed in the data ("1-piece"). The test can be added now on the TOML and carries over unchanged.
- **Not checked:** brand names and codes. They legitimately differ: IKEA is written in Thai script, and "AAC" appears only in the English.
- **Whether the two mean the same:** a person, or a review. No test can check that.

## Errors stay one plain line naming the file (rule 8)

The loader runs each data file one statement at a time and remembers `table + rowid → file:line`.
- **A constraint error while loading:** `materials.data.sql line 412: CHECK constraint failed: a price is 0 or more`.
- **A broken link, after loading:** `PRAGMA foreign_key_check` gives the table and rowid, so the line is known: `room.data.sql line 88 (room_wall_item): product 'no_such' is not in materials_product`.
- **A check view:** each view belongs to one part's schema, so its message is reported with that part's data file. A view returns no rowid, so it gives no line number. Instead its message names the row by id: `room.data.sql: wall main_wall has items but isn't drawn`.

  - `mise run dump` writes it back to the data files in the generated layout.
  - A row added in a GUI lands at the end of its table. Rows that need a place in the order are moved in the text.

## The code after

- **`common.py`:**
  - `load(db, schema, data)`: statement by statement, recording each row's line
  - `checks(db)`: foreign keys, then every `check_*` view
  - `dump(db, part)`: the generated layout
  - `placeholders`
  - `Labels` read from a label table
  - headings and notes as now
- **Each part:** `load(db)` queries its own tables (`ORDER BY rowid`) into the same dataclasses as today. Rendering and the design rules are unchanged.
- **materials.py:** reads the status flags from `materials_status` (no `STATUS` dict).
- **build.py:** opens `:memory:`, loads the six files in order, runs the checks, hands the products to the room (as today), then writes the page and the PDF.

## The tests after

- **Tests edit the SQL text and reload it.** They don't change rows in a loaded database. Two reasons:
  - The loader's file-and-line errors are exercised by every checker test.
  - A test can put a row at a position. Today's "an item moved onto the column" and "inserting a step renumbers it" put a row at the front, and a SQL `INSERT` can only add at the end.
- **Finding the row to edit:**
  1. The harness loads the real files and finds the row by what it is, never by position (rule 9).
  2. It takes that row's line from the loader.
  3. It writes the changed row with `dump` and replaces or inserts lines in the text.
- **The checker tests:** each breaks a row and expects the rule's own name, read from the schema.
- **The design-rule and behaviour tests:** keep their ideas and expectations; only their edit line changes.
- **Tests that go:**
  - "a number where text goes" (SQLite accepts it, as above)
  - "a value where a table goes" and "… a list goes" (no nesting)
- **New tests:**
  - every data file equals its own dump
  - an error names the right file and line, for a load error and for a broken link
  - `sqlite_version` is at least 3.37
  - a missing value can't pass a rule: for each optional column with a rule, a row without it loads and a row with a bad value doesn't
  - each one-row table with no row stops the build
  - the Thai/English placeholders-and-numbers test
