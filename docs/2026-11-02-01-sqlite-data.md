# 2026-11-02-01-sqlite-data.md

Plan: the quote's data as normalised SQL data files, loaded into SQLite on every build.

**Status:** proposed, 2 November 2026. It replaces the decision against in `2026-11-01-01-sql-data.md`.

**The proof** is in `etl/`, committed and run on today's real data:
- `etl/schema/` holds the design.
- `etl/migrate.py` is the TOML → SQL migration.
- `etl/fidelity.py` checks that every TOML value arrives.
- `etl/prove.py` holds the deliberate breaks.

The build, the quote and the TOML are unchanged until the switch (see "The switch").

## Why

The TOML is structured, but its shape isn't a database's. Today the rules are enforced by our own code: `common.check`, the field declarations, and each part's hand-written checks.

A normalised schema makes most of those rules the shape of the data itself. Types, required values, links, a shape's positions and a missing language are then refused by SQLite. The code that's left is the code that's about the bathroom.

The first plan was dropped mainly because SQL text is harder to read. Its own decision 2 had already accepted that cost, since the files are mostly edited by Claude and the owner reads the PDF. Labour, added since, links to both the room and the materials list, which is the kind of data a database is built for.

## Decisions, and why

1. **The data files are the only thing saved.** Each part has a schema file and a data file of plain SQL, one `INSERT` per line, committed in the repo. A database file is never committed: it's binary, so git can't show or merge it.
2. **The database is built from the files every time it's used.** That means every build, test and check: the schema files are loaded, then the data files, into an in-memory SQLite database that's thrown away afterwards.
3. **Every change is a change to the data files.** To find what to change, build the database and query it. To check the change, `mise run check` builds the database again and refuses anything wrong.
4. **Entities have random keys; the schema's vocabulary is readable codes.**
   - An entity (a product, an item, a wall, a step, a rate, a line) has `id TEXT PRIMARY KEY` of 16 hex digits, made by SQLite (`lower(hex(randomblob(8)))`). The key never changes and carries no meaning. Every link is a foreign key to it.
   - A code is part of the design, and the code is written against it: a shape, a status, a measure, a norm, a take-off, a label, a language. Changing a code is a design change (a migration).
   - Why random keys: renaming is common here. Of 80 commits that touched the data, several renamed ids; `heater_stop_tap` → `heater_stop_valve`, for example, because the trade's word changed. With random keys a rename is one row.
   - Why codes are readable: the code depends on them, so they are part of the design, like column names.
5. **Nothing in the code depends on an entity's key.** Behaviour comes from facts:
   - a status's flags (to buy, paid, on site, by the trade), not its code;
   - a unit's measure (area, length, count, job, share), not its spelling. This removes today's `"metre"` and `"m2"`, which link labour to the materials list and to the room only because they're spelt the same.
6. **Text in a person's language is never on an entity's row.** It lives in a translation table with the language in its key: `<thing>_text` (required in every language), and `<thing>_note`, `_name`, `_by` and `_plural` (in every language, or in none). Text that is the same in every language (a standard's number, a url, a drawing letter) may sit on the row.
7. **English and Thai change together.** `mise run check` compares the text tables with the last commit. A thing whose English changed but not its Thai (or the reverse) is refused.
8. **Order is a position** (`pos`):
   - It is unique within its parent: a step within its phase, an item within its wall, a product within its labour line.
   - Positions are written with gaps (10, 20, 30 …), so inserting a row between two others changes that one line.
   - The ETL and the dump write positions; nobody types them.
   - Every query that needs order says `ORDER BY pos`. Order is never taken from how SQLite happens to return rows.
9. **One table per item shape.** `room_item_rect`, `_circle`, `_point`, `_zone`, `_opening`, `_step`. Each holds only that shape's positions and sizes, so the positions it needs are `NOT NULL`. An item's shape is the one table it's in.
10. **A labour line's quantity comes from exactly one of four tables:** `labour_line_take_off`, `_n`, `_count` (with its products) or `_share_product`. `times` sits on the sources that use it.
11. **A value still to be measured** (README rule 10) is a row in `<thing>_assumed`: the thing, the column, and `how` to find the real value. The check refuses a row that marks a value that isn't there.
12. **The code's vocabulary must equal the data's.** On load, each part compares its codes with the data, exactly:
    - its labels and symbols;
    - the norms (`room.NORMS`);
    - the take-offs and what each measures (`room.take_off()`).

    For now the ETL takes the statuses and their flags from `materials.STATUS`. After the switch they're data only, and the code reads the flags.
13. **A data file holds only `INSERT`s into its own part's tables,** one per line. Anything else (a `DROP`, a trigger, another part's table, two statements on a line) is refused with the file and line number.
14. **There is one layout,** written by the dump: each table in schema order, each row in its parent's order, then its own position, then its key, then its language. The data files must equal what the dump would write (load, dump, compare), which `mise run check` makes sure of.
15. **People read the data through views,** not through the raw files. Views in the schema follow the foreign keys to the names: `show_materials_line`, `show_room_item`, `show_labour_line` and `show_phases_step`. Comments in the data files naming what keys point at were tried and taken out, because they stored every name twice and brought the rename problem back into every diff.
16. **Changes are reviewed with `sqldiff`,** SQLite's own comparison tool, at two levels:
    - the tables, to see what was edited (exact and minimal: renaming a product is 1 row);
    - each version's views saved as tables, to see what it touches (every place the product's name now appears).

    `mise run diff` compares the data with the last commit both ways.
17. **Prose refers to steps and phases by key** (`{step:9a2f4db3522dc146}`). On load, every reference in every text of the phases is checked to point at a step or phase that exists. The build prints its number, as today.

## The design

The schema files in `etl/schema/` are the design; this section is a map of them. Load order: common, materials, room, labour, phases. In all, 88 tables, 24 check views and 4 reading views.

- **common:** `language`.
- **materials:**
  - settings; section text and note;
  - labels and symbols;
  - units (with their measure), shops (with `sku_pattern`), work sections;
  - statuses (with their flags);
  - products, with their text, where they're bought (`materials_product_shop`: shop and sku together) and assumed values;
  - lines (one per product, work section and status), with notes and who brings it.
- **room:**
  - the room's size; labels and symbols;
  - take-offs (codes, with their measure);
  - tiles;
  - surfaces: the floor and the 4 walls in order, then `room_wall` and `room_floor`;
  - the column, door and lintel (one row each);
  - items, with a table per shape, their names, notes and assumed values;
  - norms (codes, with their source).
- **labour:**
  - settings; section text and note; labels and symbols;
  - Factor F (with `remark`);
  - books (with `remark`);
  - units (with their measure), work sections;
  - rates, with their text and assumed values;
  - lines, with their four sources, notes and assumed values.
- **phases:** section text and note; labels and symbols; phases; steps (within their phase).

The links between parts are only the ones README rule 6 describes:
- the room → `materials_product` (tiles, door, lintel, items);
- labour → `materials_product` (counts, shares) and → `room_take_off` (take-offs).

## What SQLite enforces, and what stays in code

**The schema and its views enforce:**
- types (`STRICT`), required values, ids (16 hex digits), uniqueness;
- every link (checked after loading, so a row may point at one loaded later);
- one-row tables having their row, the 4 walls and 1 floor, at least one of each list;
- each item having exactly one shape, its shape allowed on its surface, a floor rect with no height;
- a product or its own name (not both), an item with a product not giving its own size;
- the statuses' rules for price, shop and who brings it;
- a labour line having one source, and each source measuring what its rate is priced by;
- a rate without a book being assumed;
- a kept book's rates giving a page, and other books' rates a url.

**The loader and the code check:**
1. Every translation table follows its convention: every language, or none where optional; a required text exists.
2. Every assumed value is there.
3. Every reference in the phases' texts exists.
4. A data file holds only `INSERT`s into its own part's tables, and equals the dump.
5. English and Thai change together (against the last commit).
6. The vocabulary of labels, symbols, norms, take-offs and statuses equals the code's.
7. Thai and English carry the same `{…}` placeholders and the same numbers (`common.same_facts`, unchanged).
8. Each text uses only its own placeholders, with no stray braces:
   - shop links: `{sku}`, `{sku_digits}`;
   - product details: their sizes and `{ip}`;
   - section notes: their own;
   - a book's item format: `{item}`;
   - room notes: none.
9. A shop's sku pattern is a valid pattern, and each product's sku matches its shop's.
10. The sizes the room needs from a product: a tile's `w`, `h` and `per_box`, square and in whole mm; the door's `w` and `h`; the lintel's `h`.
11. What each shape needs once its product's sizes are filled in.
12. A kept book's file exists.
13. Every unit has its English plural.

Messages name the file and tell things apart: "MOYA wall-hung basin (item 4, Main wall)", "labour line 10 (…)". They never show a key.

## The migration (ETL), for the switch only

`etl/migrate.py` does three things:
- **Extract:** it reads the four TOML files after today's code has checked them, so nothing today's checks would refuse is migrated.
- **Transform:** it reshapes them into the design. Every difference between the TOML's shape and the design is in this one place:
  - old ids → keys, and every link with them;
  - the item table → a table per shape;
  - references in prose → keys;
  - unit spellings → measures;
  - lines → ids and positions;
  - plurals and `times` moved to where they belong;
  - statuses as data;
  - the notes and remarks that are only TOML comments today, carried by hand (`HOW`, `FACTOR_F_REMARK`, `BOOK_REMARK`).
- **Load:** it puts the rows into a fresh database (the schema refuses anything that doesn't fit), dumps the data files, loads them again from nothing, and runs every check.

Keys are worked out from the old ids (the first 16 hex digits of a SHA-256 of the kind and the id). So running the ETL again gives the same keys, and the files don't churn while the design changes. The ETL is rerun until the design is right, then once more at the switch. After that it is retired and kept only in git history.

**Proof, on today's data:**
- `migrate.py`: 88 tables, 1,265 rows, 0 problems, the round trip (load, dump) identical.
- `fidelity.py`: each TOML file rebuilt from the database, 0 differences. Labels, symbols and assumed keys are compared as sets, since they have no order.
- `prove.py`:
  - 50 breaks made on a copy of the database, all refused by the rule meant to refuse them (12 ms each);
  - 4 broken data files, all refused with file and line;
  - inserting a step changes 1 line;
  - English changed without its Thai is caught.
- SQLite's own command-line tool loads the files with none of our code: integrity check ok, 0 broken links.

## After the switch: changing the design

A design change is a numbered step in `migrations/`:
- the new schema;
- and, where a plain copy isn't enough, the step's SQL (splitting a column, filling a new one).

`mise run migrate` then:
1. loads today's data under the current schema;
2. builds a fresh database from the new schema;
3. copies every row across by table and column name;
4. runs the step's SQL and every check;
5. dumps the data files.

Nothing is written if a check fails. The data files record the step they're at, and a test replays the steps from step 0 (the ETL's output) and compares the result with the files.

Ready-made migration tools were tried on this schema on 2 November 2026; none fits:

| Tool | Version, released | Result |
|---|---|---|
| sqldef | 3.11.29, 30 Oct 2026 | its parser fails on `GLOB` in the first table |
| Atlas | 1.3.0, 29 Jul 2026 | "views are available to logged-in users only" |
| dbmate | 2.37.0, 18 Oct 2026 | changing a rule failed: SQLite won't rebuild a table a view uses (rolled back safely) |
| goose | 3.29.0, 11 Oct 2026 | same as dbmate |
| sqlite-utils `transform` | 4.2.1, 13 Aug 2026 | rebuilds columns safely, but not a changed rule |
| Alembic | 1.20.1, 22 Oct 2026 | needs SQLAlchemy models, a second copy of the schema |
| yoyo | 9.0.0, Aug 2024 | no release in two years |

All of them alter a long-lived database in place. Ours is rebuilt from text every time, so building the new design fresh and copying the data across is simpler and can't hit the view problem. That's a few dozen lines of our own; it's the least-worst option.

## Tools

**`sqlite-tools` 3.54.1** (16 Oct 2026), from sqlite.org's own download: `sqlite3`, `sqldiff` and `sqlite3_analyzer`, ready-made for Linux and both kinds of Mac. mise pins it from the URL, per platform (`http:sqlite-tools`). Python's own `sqlite3` module (SQLite 3.53.1 in the pinned Python) runs the build. No new Python package is needed.

## Tests after the switch

- Each test copies the loaded real database (SQLite's `backup`, well under a millisecond) and breaks it with plain SQL. It expects the refusal of the rule it breaks, worked out from the real data (rule 9). It finds what it breaks by what it is: "an item with a product on a wall", never "the basin".
- Tests of the loader break copies of the data files.
- Two tests that put a row first ("an item moved onto the column", "inserting a step renumbers it") set its position.
- `test_pipeline.py` today edits TOML through `data(lambda d: …)` in 88 places, and every one is rewritten. The expectations stay; only how each test breaks the data changes.

## The switch, as one change

1. Run the ETL one last time, and commit its data files and the schema files.
2. Rewrite the four parts' loaders to read the database, not the TOML, into the same objects as today. Rendering, the room's geometry, the design checks and the drawings are unchanged.
3. Remove what the schema now enforces from the code: `common.check`, the field declarations, the hand checks listed above as moving, and `STATUS`. Keep the checks under "The loader and the code check".
4. `build.py` builds the database once, hands each part what it needs, and passes the room and the materials list along as today (rule 6).
5. Add `mise run diff` and `mise run migrate`; `mise run check` gains the dump comparison and the English and Thai check. Pin `sqlite-tools` in `mise.toml`.
6. Rewrite `test_pipeline.py` as above.
7. Rewrite the README:
   - the Files table and How the quote is made;
   - rule 1 (data files);
   - rule 2 (consistency is the schema plus the dump layout);
   - rule 3 (names as translation tables; English and Thai change together);
   - rules 5–7 (data file now means a part's two SQL files; keys and codes);
   - rule 8 (messages name the file and the thing);
   - rule 9 (tests copy the database);
   - rule 10 (assumed values with `how`);
   - Checks (which checks are the schema's and which the code's).
8. Delete the TOML and `etl/`.
9. **Prove it:**
   - `out/index.html` is byte-identical to today's, except where the page says "generated from room.toml" (it then names the data file);
   - the PDF's text (`pdftotext`) is identical apart from that;
   - `mise run ci` is clean, with 0 design problems;
   - each new check is shown to fail when broken;
   - an independent review;
   - the GitHub build is green.

## Open

- **Rule 5 in one database.** Any part's code could query any table. The boundary holds by convention: each part reads only its own tables and the links in rule 6. A test could check each part's queries name only those tables.
- **Prose references read as keys** (`{step:9a2f…}`). They're checked on load, but writing one by hand means looking up the key with a query.
- **`how` is filled for 3 of the 10 assumed values.** The TOML has notes only for the heater's IP rating and the shower head. The others (the floor's falls, the shower zone's waterproofing, the disposal rate, the old wall's area, the old tiles, the pipe runs) need a note written before the switch.
