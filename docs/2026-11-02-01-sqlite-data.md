# 2026-11-02-01-sqlite-data.md

Plan: the quote's data in a normalised SQLite database that runs here and on Cloudflare D1, kept in git as migrations and seed files.

**Status:** proposed, 2 November 2026 (round 5: round 4, with the independent review's 15 findings fixed). It replaces the decision against in `2026-11-01-01-sql-data.md`.

**The proof** is in `etl/`, committed and run on today's real data:
- `etl/schema/` holds the design.
- `etl/migrate.py` is the TOML → SQL migration (the ETL), and the shared database code.
- `etl/edit.py` is the working database: `load`, `save`, `status`, `sql`, `show`, `diff`, `lint`, `migrate`.
- `etl/d1.py` pushes the data to D1, runs the checks there and pulls it back.
- `etl/features.py` runs window functions, a recursive CTE, a generated column, an upsert, a trigger and a view on the real data, on all three engines.
- `web/` is the web app: a Hono Worker with HTMX 4 on the same D1, using the Sessions API for read replicas; `web/test_web.py` tests it end to end.
- `etl/fidelity.py` proves every TOML value arrives.
- `etl/prove.py` holds the deliberate breaks.

Each has a mise task (`mise tasks` lists them as `db:…` and `etl:…`). The build, the quote and the TOML stay unchanged until the switch (see "The switch").

## Why

The TOML is structured, but its shape isn't a database's. Today the rules are enforced by our own code: `common.check`, the field declarations, and each part's hand-written checks.

A normalised schema makes most of those rules the shape of the data itself. SQLite then refuses wrong types, missing values, broken links, clashing positions and missing languages. What's left in the code is the code about the bathroom. Changing it gets easier, because the database won't accept a wrong shape.

The quote will also move to Cloudflare, whose database, D1, is SQLite. A design that loads and checks on D1 today is one that moves without a second redesign.

## Decisions, and why

1. **Git keeps the schema as migrations and the data as seed files**, the layout Cloudflare's own tool (`wrangler d1 migrations`) uses.
   - `migrations/0001_initial.sql`, `0002_…` hold the schema: every table, view and index, with each explanation inside its `CREATE` statement. A schema change is always a new numbered file; an applied one never changes.
   - `data/common.sql`, `materials.sql`, `room.sql`, `labour.sql` and `phases.sql` hold the data. Each is exactly what `sqlite3 quote.db ".dump --data-only <part>_%"` writes: one `INSERT` of plain values per row.
   - Binary `.db` files are never committed (`*.db` in `.gitignore`); they can't be diffed or merged.
   - So every table and view is named after its part (`materials_…`, `room_check_…`, `common_language`).
2. **Read and write the working database, `.work/quote.db`, and save it to the seed files.** `.work/` is never committed.
   - `mise run db:load` makes it from the migrations and the seed files: after a pull or a fresh clone. `db:load --discard` throws unsaved changes away.
   - Read and change it with any SQLite tool, or `mise run db:show "…"` and `mise run db:sql "…"`. `db:sql` runs as one transaction with the functions in decision 9; on any error nothing changes.
   - `mise run db:save` checks it and writes the seed files, or writes nothing and says why (decision 3).
   - `mise run db:status` says whether it holds unsaved changes, judged against the data as loaded (or last saved). A pull that changes the seed files isn't a change in `quote.db`. `mise run db:diff` shows the changes as SQL (`sqldiff --primarykey`, so each row is named by its key).
3. **Guards keep the database and the files from drifting apart.**
   - `load` refuses to overwrite `quote.db` while it holds unsaved changes.
   - `save` refuses, writing nothing, when:
     - the seed files changed since `load` (a `git pull` or checkout), because saving would undo that change. `load` keeps a fingerprint of the files beside `quote.db`;
     - its schema isn't the migrations', whether a table was changed by hand or there's a migration it hasn't had (then run `db:migrate`);
     - anything is wrong: a broken link (so a tool that leaves foreign keys off can't save one), a check view, the translation rules, a code the code doesn't know, a table that belongs to no part (it would be lost from the seed files), or anything today's checks in the parts' code refuse (a sku unlike its shop's, a placeholder a text can't fill, a tile with no size). In the trial these run in `migrate.py`; at the switch, `save` runs the parts' own loaders, the same as the build;
     - a text changed in one language only, unless `save --alone`, which names each one for the commit message (a Thai typo fixed, say). It's judged against the data as loaded, which `load` copies beside `quote.db`.
   - Then `save` dumps to a folder beside the seed files, loads that back as a build would and checks it again. Only then does it move the five files into place, one after another (if that is ever interrupted, git shows the mix).
   - At the switch, `publish` refuses while `db:status` reports unsaved changes. `check`, `ci` and GitHub always build a fresh database from the files, so what's checked is what's committed.
4. **Entities have UUID keys; the schema's vocabulary is readable codes.**
   - An entity (a product, an item, a wall, a step, a rate, a line) has `id TEXT PRIMARY KEY`, a UUID made by SQLite itself (a v4 default on every table, built from `randomblob`, which D1 runs too). A rule refuses anything that isn't the 8-4-4-4-12 small-hex shape.
   - The key never changes and carries no meaning. Every link is a foreign key to it.
   - A code is part of the design, and the code is written against it: a shape, a status, a measure, a product's kind, a norm, a take-off, a label, a language. Changing a code is a design change (a migration).
   - Why random keys: renaming is common here. Several of the commits that touched the data renamed ids; `heater_stop_tap` → `heater_stop_valve`, for example, because the trade's word changed. With random keys a rename is one row of text.
5. **Nothing in the code depends on an entity's key.** Behaviour comes from facts:
   - a status's flags (to buy, paid, on site, by the trade), not its code;
   - a unit's measure (area, length, count, job, share), not its spelling. This removes today's `"metre"` and `"m2"`, which link labour to the materials list and the room only because they're spelt the same;
   - a product's kind (door frame, lintel, tile): the door must name a door frame, the lintel a lintel, a tile a tile. What a product is belongs to the product, so its kind is on the materials list; the rule that the door names a door frame is the room's.
6. **Text in a person's language is never on an entity's row.**
   - It lives in a translation table with the language in its key: `<thing>_text` (required in every language); `<thing>_note`, `_name`, `_by` and `_plural` (in every language or in none; a plural only where a language has one); and each part's `_label` (every code in every language).
   - No text anywhere may be empty: every text column has its own rule. A text is one line: a line break or tab is refused (`.dump` would write it as `unistr(…)`, which isn't a plain value).
   - Text that is the same in every language (a standard's number, a url, a drawing letter) may sit on the row.
   - So may a note for whoever edits the data or measures on site (`how`, `remark`): English only, never printed.
7. **English and Thai change together**, each text on its own: a product's Thai name and English detail changing is refused, though each row has both languages changed. It's checked twice:
   - by `save`, against the data as loaded;
   - at the switch, by `mise run check`, against the commit before the push (`github.event.before` on GitHub, `origin/main` locally).
8. **A link inside text is a row, not text.** A step's text, or a phase's note, that refers to another step or phase has a numbered gap (`{1}`, `{2}` …). A `_ref` row says what each gap points at, with a foreign key.
   - The text reads normally in both languages; renaming or moving a step changes nothing in it.
   - SQLite enforces the link; the check refuses a gap without its row, or a row without its gap.
9. **Order is a position** (`pos`):
   - It's unique within its parent (a step within its phase, an item within its wall) or within its table.
   - Positions are written with gaps (10, 20, 30 …), so a new step between two others adds its own lines and changes none.
   - `db:sql` offers `new_id()`, `next_id()`, `pos_after(table, key)` and `pos_first(table, parent)`. They work keys and positions out, re-spacing a parent's rows when a gap is used up, so nobody types a position. That keeps README rule 7.
   - Every query that needs order says `ORDER BY pos`.
10. **One table per item shape:** `room_item_rect`, `_circle`, `_point`, `_zone`, `_opening`, `_step`. Each holds only that shape's positions and sizes, so they are `NOT NULL`.
11. **A labour line's quantity comes from exactly one source:** `labour_line_take_off`, `_n`, `_count` (with its products) or `_share` (with its products). A count can't mix products bought by length with products counted.
12. **A value still to be measured** (README rule 10) is a row in `<thing>_assumed`: the thing, the column, and **how** to find the real value, which is required. A row marking a value that isn't there is refused.
13. **The code's vocabulary equals the data's:** labels, symbols, norms, and the take-offs with their measure. These codes are held in both, a stated exception to README rule 7, and the check keeps them equal; a label in the data that the code doesn't use is refused too. The statuses are data only, and the code reads their flags.
14. **A seed file may hold only rows of plain values for its own part's tables, one per line**, as `.dump --data-only` writes them. A view, a trigger, a query, an upsert, another part's row or two rows on a line is refused, with the file and line.
15. **Each part's code reads only its own tables.** What one part needs from another (the room: product names, sizes and IP ratings; labour: the take-off and the list's counts) is read by `build.py` from the part that owns it and handed over, as today (rules 5 and 6). SQLite's authorizer refuses any other read, including one through a view.
16. **The layout is SQLite's.** The seed files must equal what `.dump` writes of the database loaded from them (load, dump, compare).
17. **People read the data through views** that follow the foreign keys to the names: `materials_show_line`, `room_show_item`, `labour_show_line`, `phases_show_step`; `room_show_fitting`, `common_show_product_reach` and `phases_show_text` (decision 23). `mise run db:show` reads them in the working database, `mise run db:show-d1` on Cloudflare (`etl:show-d1` on the trial's local D1).
23. **Recursive queries wherever the data needs a step repeated until it stops.** A recursive query does one job, so each place was judged by whether the data repeats a step. Four views use `WITH RECURSIVE`, three for the chain of fittings (an item serves another, a stop valve the basin, and nothing limits how deep a chain goes), one for the references in text:
    - `room_check_fitting_loop` refuses a chain that comes back to its start (A serves B, B serves A). Before, only an item serving itself was refused; a loop would send any code following the chain round for ever. The query stops at the start, or at an item it has passed, so it ends even on a loop.
    - `room_show_fitting` gives each chain as a tree, flat and in order, with each item's depth and the chain from the fitting down. It's the shape a page draws a thread from (indent by depth), and at the switch, code that needs a chain (the design check that a part sits within its fitting) reads it here instead of walking the links itself.
    - `common_show_product_reach` gives everything a change to a product reaches: the items using it and, down each chain, the items serving them; its tile, door or lintel; its lines on the materials list; the labour lines priced from it. It reads every part, so it belongs to none: it's for review, alongside `db:diff`, and no part's code reads it.
    - `phases_show_text` gives each step's text and each phase's note, in each language, as the quote prints them: the gaps filled one at a time ({1}, then {2} …) with the number of the step ("2.3") or phase ("2") each points at. All 100 texts equal what today's `phases.py` prints (`etl:fidelity`). At the switch, `phases.py` reads them here, and its own `resolve()` goes; the printed text no longer depends on the code's language, and D1 gives the same.

    Places looked at and left out, and why:
    - **Tile joints along a wall** (a joint every tile from the corner, for the hole-near-a-joint check) are a repeated step, but they are worked out from the door's position, which `room.py` sets out (README rule 1), and the check is a design check, which is code. Joints in SQL would split the room's geometry between two places (rule 7). It becomes right only if the room's geometry as a whole moves into the database.
    - **The schema's own links** (that parts link only as README rule 6 allows) can't be a view: D1 refuses a query that feeds table names into its schema functions ("not authorized"). It is a check in the shared code instead, with no recursion needed: every foreign key between parts must be room → `materials_product`, labour → `materials_product` or labour → `room_take_off`.
    - **Numbering** (phases, steps, items, lines) is window functions (`row_number`, `dense_rank`), not recursion.
18. **Changes are reviewed with `sqldiff --primarykey`:** `db:diff` shows the working database against the seed files, as SQL that names each row by its key (a `rowid` isn't stable).
19. **Messages name the file and tell things apart:** "MOYA wall-hung basin (item 4, Main wall)", "labour line 10 (…)". A message from the checks never shows a key.
20. **Every foreign key has an index**, because the data will grow. `mise run db:lint` runs SQLite's own `.lint fkey-indexes`, which prints nothing: 50 indexes.
    - In every view, each join to a table looks its rows up by an index (87 lookups).
    - Five joins are on a `UNION` of the one-to-one tables (an item's shape, a line's source). A `UNION` has no index of its own, so SQLite makes one for each query.
    - Each check view reads its main table in full, as a check of every row must.
21. **Designed for Cloudflare D1 from now.** Everything below was tried on wrangler 4.156.0's local D1:
    - `STRICT` tables, the UUID default, views and named rule messages all work.
    - D1 always has foreign keys on and runs a file as one transaction. `PRAGMA defer_foreign_keys = true` lets a row come before the one it points at; our loader does the same.
    - D1 allows at most 5 terms in a compound `SELECT` (found by trying; not in its documentation). Every view keeps to that, using `VALUES` lists and nested groups.
    - D1's limits: a statement of 100,000 bytes, 100 bound values, 100 columns, 32 function arguments, a `LIKE` pattern of 50 bytes, a row of 2 MB, a database of 10 GB. Our loader sets the same limits on every database it opens (`setlimit`), so anything D1 would refuse is refused here first.
    - Tried on 2 Nov 2026 with Thai text, the same on `sqlite3` 3.54.1, Python's SQLite 3.53.1 and local D1 (which refuses `sqlite_version()`: "not authorized to use function"):
      - `INSERT … RETURNING` gives back the new UUID. The code will use it; `new_id()` stays for SQL typed into `db:sql`, where the next statement needs the key.
      - Full-text search (FTS5) with its default tokenizer finds nothing in Thai, which has no spaces between words. The `trigram` tokenizer finds Thai words (3 characters or more). Any search added later uses `trigram`.
      - JSON (`->>`) works, but no column holds JSON: it would hide values from types, rules and foreign keys.
    - **Window functions, recursive CTEs, generated columns, upserts, triggers and views**, run by `etl/features.py` on the real data, identical on Python's SQLite, `sqlite3` and local D1. A migration made for the test adds a generated column and an `updated_at` stamped by a trigger; then a price is updated and a label is written twice by an upsert, on each engine:
      - a running total of the priced products and each one's rank by price within its unit (52 rows);
      - the schema's recursive views: `room_show_fitting` (9 rows), `common_show_product_reach` (105 rows) and `phases_show_text` (100 rows); and a loop of fittings made on each engine, caught by `room_check_fitting_loop` run by that engine, D1 included;
      - a migration adding a product's face area as a `VIRTUAL` generated column with an index: a lookup by area uses the index (10 rows). `.dump --data-only` and `wrangler d1 export` both leave generated values out, so the seed files load unchanged under the new schema and dump back identical. `ALTER TABLE … ADD COLUMN` can add a `VIRTUAL` generated column; a `STORED` one needs the table rebuilt in its migration. A plain column added by a migration makes the old seed rows one value short (they list values by position), which is why a migration goes `db:migrate` then `db:save`;
      - an upsert (`INSERT … ON CONFLICT … DO UPDATE`) writing a label twice: the second write updates the first, with no error, 2 rows (one per language);
      - a trigger stamping `updated_at` when a product's price or size is updated: exactly the 1 updated product is stamped;
      - `materials_show_line`, the materials list as people read it (62 rows);
      - the seed-file cycle: the migrated, changed data dumps, loads from nothing without the trigger firing (an `INSERT` isn't an `UPDATE`, so the stamp is kept), and dumps back identical.
    - **Triggers live in migrations** and follow two rules the checks enforce: a trigger fires on `UPDATE` only (a load inserts every row and `db:push` deletes every row, so an `INSERT` or `DELETE` trigger would change the data each time), and it changes only its own part's tables (README rule 5). **Upserts** are for the code and `db:sql`; a seed file holds plain rows only (decision 14).
    - **Proof:** `mise run etl:d1` applies the migrations to the local D1 and replaces its data with the seed files. D1 then runs all 27 check views itself (0 problems), its schema equals the migrations', and its 91 tables' row counts match. The data exported back (`wrangler d1 export`) is the seed files exactly. A price changed on D1 shows in the pull as one line of SQL.
22. **Sync between here and Cloudflare: git keeps the truth, and nothing is wiped.** The web app (decision 24) writes to D1, so D1 can hold changes git hasn't had yet.
    - `mise run db:push` refuses while the working database holds unsaved changes, while git doesn't hold the seed files and migrations as they are, or if they fail any check; and it refuses if D1's data is neither the seed files nor any version of them in git's history — a change made on D1 itself, which a push would wipe. All before anything is sent. Then it applies the migrations D1 hasn't had (`wrangler d1 migrations apply --remote`), makes D1's data exactly the seed files, as one file, and checks D1: its schema against the migrations (a change no migration made, or a migration edited after D1 had it, is caught), the check views and the row counts.
    - `mise run db:pull` exports D1 and shows how it differs from the seed files: first the schema, then the data, as SQL (wrangler's own tables, `d1_migrations` and Cloudflare's `_cf_…`, left out). Then it takes D1's data into the working database, judged against the seed files, so `db:diff` shows it and `db:save` checks it like any other change — every rule, Thai and English together — before it reaches the seed files and git. Nothing from D1 is committed unchecked.
    - The real D1 database isn't made yet. `db:push` and `db:pull` refuse until it is (`wrangler d1 create bathroom-quote`, its id in `wrangler.toml`). Making it is the owner's decision.

24. **The web app: Hono and HTMX 4 on D1, with read replicas from day 1.** `web/src/index.ts` is a Hono Worker (`main` in `etl/wrangler.toml`, the same D1 binding as the data), pinned in `web/package.json` and `package-lock.json`: Hono 4.13.16, htmx 4.0.1 (served by the Worker itself, no third-party script host), TypeScript 7.0.2 with Cloudflare's Workers types.
    - **Three pages, switched in place by HTMX 4's morph swap:** the materials list, the schedule of fittings (`room_show_fitting`: each chain of fittings as a tree, indented by depth), and the scope of works (`phases_show_text`: each phase's heading and note, its steps numbered in Thai and English columns, every reference filled). The two recursive views are read through the same D1 session as everything else, so on Cloudflare they are served by the nearest read replica — they read many rows to give a few, which is what replicas are for — and still include the visitor's own writes. `room_show_fitting` gives each item in each language for this.
    - **The materials list, off the real data:** the materials list still to buy — each product in Thai with its English under it, the quantity with its unit and plural, the price (marked approximate where it is), the running total still to buy (a window function run by D1), and the total rounded and marked "about" as the PDF gives it (฿23,900 on today's data, the same as the PDF). Each line has a ✓ to mark it on site: it writes to D1, and the fresh list comes back in its place.
    - **Every word on the page comes from the database:** the materials part's labels, symbols and section text (README rule 1). What a status means is read from its flags; the write picks "paid and on site, not to buy", never a status code (decision 5). It moves only a line still to buy whose product has a price and a shop, so the write can't leave a problem behind.
    - **Read replicas, safely:** every request runs in a D1 session (`withSession`), started from the bookmark in the visitor's cookie (or `first-unconstrained`), and hands back the session's latest bookmark (`getBookmark()`) in that cookie — after reads as well as writes. So a visitor's reads only go forward and always include their own writes, even when a replica that is behind serves them. Writes always go to the primary. Read replication itself is switched on per database (dashboard, or the API's `read_replication.mode: auto`), on the real database once it exists.

Then the change travels back: `db:push` refuses to wipe it, `db:pull` shows it as one row and takes it in, `db:save` checks it and writes the seed files, and `db:push` is allowed again. `mise run web:check` type-checks the app.
    - **Tasks:** `web:setup` (install the pinned packages), `web:check`, `web:dev` (serve it on local D1), `web:test`, `web:deploy` (on Cloudflare, once the database is there).

## The design

The schema files in `etl/schema/` are the design; this is a map of them. Load order: common, materials, room, labour, phases. 91 tables, 27 check views, 7 reading views, 2 helper views (an item's shape, a line's source), 50 indexes.

- **common:** `common_language`, the conventions every table follows, and `common_show_product_reach`.
- **materials:** settings; section text and note; labels and symbols; units (with measure and plurals), shops, work sections; statuses (with their flags); products (with kind), their text, where they're bought and assumed values; lines, with notes and who brings each.
- **room:** the room's size; labels and symbols; take-offs (with measure); tiles; surfaces (the floor and the 4 walls in order, then `room_wall` and `room_floor`); the column (with `remark`), door and lintel; items, with a table per shape, names, notes and assumed values; norms (with their source).
- **labour:** settings; section text and note; labels and symbols; Factor F (with `remark`); books (with `remark`: how to take in a new edition); units, work sections; rates, with their text and assumed values; lines, with their four sources, notes and assumed values.
- **phases:** section text and note; labels and symbols; phases; steps; the references in step texts and phase notes.

The only links between parts are README rule 6's: the room → `materials_product`; labour → `materials_product` and `room_take_off`.

## What SQLite enforces, and what stays in code

**The schema and its check views enforce** (on D1 too):
- types (`STRICT`), required values, UUID keys, no empty text, uniqueness, positions unique within their parent;
- every link, including references in text; no item serving itself, no step referring to itself;
- one-row tables having their row; exactly 4 walls and 1 floor, a wall's row on a wall surface and the floor's on the floor;
- each item having exactly one shape, allowed on its surface; a floor rect with no height;
- a product or its own name, not both; an item with a product taking its size from it;
- the door, lintel and tiles naming a product of their kind;
- the statuses' rules for price, shop and who brings it;
- a labour line having one source, measuring what its rate is priced by, and a count not mixing measures;
- a rate without a book being assumed; a kept book's rates giving a page, other books' a url;
- every assumed value having its `how`.

**The shared code checks** (Python today, in the language chosen later). These loop over every table, which one view can't do:
0. every table, view, index and trigger belongs to a part; every foreign key between parts is one README rule 6 allows; a trigger fires on `UPDATE` only and changes its own part's tables only; no text holds a line break or tab;
1. each translation table and label follows its convention; every unit has its English plural;
2. every assumed value is there;
3. every gap in a text has its reference row, and every row its gap, in each language;
4. Thai and English carry the same `{…}` placeholders and numbers (`common._facts`), and no brace opens or closes nothing;
5. a seed file holds only its part's rows and equals the dump;
6. English and Thai change together;
7. the vocabulary equals the code's.

**Today's checks in the parts' code, moved unchanged at the switch:** each text uses only its own placeholders; a shop's sku pattern is valid and each sku matches it; the sizes the room needs from a product; what each shape needs once its product's sizes are filled in; a kept book's file exists. The first three also run in the trial's checks, so `save` refuses what the build would.

## The migration (ETL), for the switch only

`etl/migrate.py`:
- **Extract:** reads the four TOML files after today's code has checked them (`build.assemble(md, measure=False)`), so nothing today's checks refuse is migrated.
- **Transform:** reshapes them into the design. Every difference between the TOML's shape and the design is in this one place: old ids → UUIDs; the item table → a table per shape; references in prose → gaps and ref rows; unit spellings → measures; the room's slots → product kinds; plurals, `times` and statuses moved to where they belong; and the notes that are only TOML comments today, carried by hand (`HOW`, `FACTOR_F_REMARK`, `BOOK_REMARK`, `COLUMN_REMARK`).
- **Load:** writes `migrations/0001_initial.sql` from `etl/schema/`, puts the rows into a database built from it, and writes the seed files with `sqlite3 .dump --data-only`. Then it loads them again from nothing, as D1 would, and runs every check.

Migrated keys are UUID v5 of the kind and the old id. Running the ETL again gives the same keys, so the files don't churn while the design changes; keys made after the switch are v4. The ETL is rerun until the design is right, then once more at the switch, and is then retired.

## After the switch: changing the design

1. `mise run db:migration <what-it-does>` starts the next numbered file (wrangler's own command).
2. Write the change in SQL, and the SQL that moves the data, if a plain change isn't enough. A migration that rebuilds a table drops and re-creates the views on it. A migration changes the schema only and never puts rows in a table (on a load from nothing the seed files would add them a second time); a new code or label is data, added with `db:sql` and saved. To redo a migration while writing it: `db:load --discard`, edit it, `db:migrate` again.
3. `mise run db:migrate` runs it on the working database; `mise run db:save` checks everything and writes the seed files in the new shape.
4. On Cloudflare, `mise run db:push` applies it to D1 and sends the data.

On a load from nothing, the migrations run on empty tables and the seed files fill them. So the seed files are always in the latest schema, and a fresh load and D1 hold the same.

Seven ready-made migration tools were tried on this schema on 2 November 2026: sqldef, Atlas, dbmate, goose, sqlite-utils, Alembic and yoyo. None fits. They failed on `GLOB`, wanted a login for views, couldn't rebuild a table a view uses, or needed a second copy of the schema. Cloudflare's `wrangler d1 migrations` is the one that does fit: it's the tool D1 uses, and the trial runs its numbered files.
