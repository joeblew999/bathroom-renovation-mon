# 2026-11-02-01-sqlite-data.md

Plan: the quote's data in a normalised SQLite database, kept in git as SQLite's own dump of each part.

**Status:** proposed, 2 November 2026. It replaces the decision against in `2026-11-01-01-sql-data.md`.

**The proof** is in `etl/`, committed and run on today's real data:
- `etl/schema/` holds the design.
- `etl/migrate.py` is the TOML → SQL migration and the shared database code.
- `etl/edit.py` holds the working database's commands: `load`, `save`, `status`, `sql`, `show`.
- `etl/fidelity.py` proves every TOML value arrives.
- `etl/prove.py` holds the deliberate breaks.

The build, the quote and the TOML are unchanged until the switch (see "The switch").

## Why

The TOML is structured, but its shape isn't a database's. Today the rules are enforced by our own code: `common.check`, the field declarations, and each part's hand-written checks.

A normalised schema makes most of those rules the shape of the data itself. Types, required values, links, a shape's positions and a missing language are then refused by SQLite. The code that's left is the code that's about the bathroom, and changing it is easier because the database won't accept a wrong shape.

The first plan was dropped mainly because SQL text is harder to read. Its own decision 2 had already accepted that cost, since the files are mostly edited by Claude and the owner reads the PDF. Labour, added since, links to both the room and the materials list, which is the kind of data a database is built for.

## Decisions, and why

1. **What's kept in git is SQLite's own dump of each part.** That's the standard way to version an SQLite database: a binary `.db` file is kept out of git (it can't be diffed or merged), and the plain-text SQL dump that rebuilds it is committed.
   - Each part has one file, `common.sql`, `materials.sql`, `room.sql`, `labour.sql` and `phases.sql`. Each is exactly what `sqlite3 quote.db ".dump <part>_%"` writes: the part's tables, views and data, as standard SQL.
   - So every table and view is named after its part (`materials_…`, `room_check_…`, `common_language`), and every explanation sits inside its `CREATE` statement, where SQLite keeps it. Comments between statements would be lost; all 108 survive.
   - The files are written only by SQLite's `.dump`; nobody edits them by hand. They're rebuilt with `sqlite3 quote.db < materials.sql` and so on, or by our loader, which reads them in the same way.
2. **Read and write the working database, `out/quote.db`; save it to the part files.** `out/quote.db` is never committed.
   - Read it and change it with any SQLite tool: SQLite's own `sqlite3`, a SQLite browser, or SQL (`mise run sql "…"`, which also offers the functions in decision 9).
   - **`mise run save`** runs every check on `quote.db` (every rule, every check below, and English changed with its Thai), then writes each part's file with `sqlite3 .dump`. If anything fails, it writes nothing and says why. So a tool that leaves foreign keys off can't save a broken link.
   - **`mise run load`** rebuilds `quote.db` from the part files: after a pull, a fresh clone, or to throw changes away.
3. **Two guards keep the database and the files from drifting apart:**
   - `load` refuses to overwrite `quote.db` if it holds changes that aren't in the part files ("save them first, or delete quote.db to throw them away");
   - `publish` refuses if `quote.db` and the part files differ (`mise run status`), so nothing unsaved is pushed.

   `mise run check`, `ci` and GitHub always build a fresh database from the part files, so what's checked is what's committed. Any other database file someone opens is a throwaway, rebuilt from the files.

4. **Entities have random keys; the schema's vocabulary is readable codes.**
   - An entity (a product, an item, a wall, a step, a rate, a line) has `id TEXT PRIMARY KEY` of 16 hex digits, made by SQLite (`lower(hex(randomblob(8)))`, or `new_id()` in `mise run sql`). The key never changes and carries no meaning. Every link is a foreign key to it.
   - A code is part of the design, and the code is written against it: a shape, a status, a measure, a product's kind, a norm, a take-off, a label, a language. Changing a code is a design change (a migration).
   - Why random keys: renaming is common here. Of 80 commits that touched the data, several renamed ids; `heater_stop_tap` → `heater_stop_valve`, for example, because the trade's word changed. With random keys a rename is one row.
   - Why codes are readable: the code depends on them, so they are part of the design, like column names.
5. **Nothing in the code depends on an entity's key.** Behaviour comes from facts:
   - a status's flags (to buy, paid, on site, by the trade), not its code;
   - a unit's measure (area, length, count, job, share), not its spelling. This removes today's `"metre"` and `"m2"`, which link labour to the materials list and to the room only because they're spelt the same;
   - a product's kind (door frame, lintel, tile): the room's door must name a door frame, the lintel a lintel, a tile a tile. Today the door could name a basin as long as it has a width and height.
6. **Text in a person's language is never on an entity's row.**
   - It lives in a translation table with the language in its key: `<thing>_text` (required in every language); `<thing>_note`, `_name`, `_by` and `_plural` (in every language, or in none; a plural only where a language has one); and each part's `_label`, its fixed wording (every code in every language).
   - No text may be empty.
   - Text that is the same in every language (a standard's number, a url, a drawing letter) may sit on the row.
   - So may a note for whoever edits the data or measures on site (`how`, `remark`): English only, never printed, like the messages printed for whoever runs the build.
7. **English and Thai change together.** A thing whose English changed but not its Thai (or the reverse) is refused, labels included. This is checked twice:
   - by `save`, against the part files it would overwrite;
   - by `mise run check`, against the last published data (`origin/main`). GitHub's checkout fetches the history it needs (`fetch-depth: 0` in `pages.yml`), so the check is the same run locally and on GitHub.
8. **A link inside text is a row, not text.** A step's text, or a phase's note, that refers to another step or phase has a numbered gap (`{1}`, `{2}` …). A `_ref` row says what each gap points at, with a foreign key.
   - The text reads normally in both languages; renaming or moving a step changes nothing in it.
   - SQLite enforces the link.
   - The code checks that every gap has its row and every row its gap, in each language. The build prints the step's or phase's number in the gap.
9. **Order is a position** (`pos`):
   - It is unique within its parent (a step within its phase, an item within its wall, a product within its labour line) or within its table.
   - Positions are written with gaps (10, 20, 30 …), so a new step between two others adds its own lines and changes none.
   - `mise run sql` offers `pos_after(table, key)` and `pos_first(table, parent)`, which work positions out (re-spacing a parent's rows when a gap is used up), so nobody has to type one. That keeps README rule 7.
   - Every query that needs order says `ORDER BY pos`. Order is never taken from how SQLite happens to return rows.
10. **One table per item shape:** `room_item_rect`, `_circle`, `_point`, `_zone`, `_opening`, `_step`. Each holds only that shape's positions and sizes, so the positions it needs are `NOT NULL`. An item's shape is the one table it's in.
11. **A labour line's quantity comes from exactly one source.** The sources are `labour_line_take_off`, `_n`, `_count` (with its products) and `_share` (with its products). `times` sits on the sources that use it. A count can't mix products bought by length with products counted.
12. **A value still to be measured** (README rule 10) is a row in `<thing>_assumed`: the thing, the column, and **how** to find the real value, which is required. The check refuses a row that marks a value that isn't there.
13. **The code's vocabulary equals the data's.** On load, each part compares, exactly:
    - its labels and symbols;
    - the norms (`room.NORMS`);
    - the take-offs and what each measures (`room.take_off()`).

    These codes are held in both the code and the data. That's a stated exception to README rule 7's "every fact once": the check keeps the two equal. The statuses are data only, and the code reads their flags. During the migration, the ETL compares them once with today's `materials.STATUS`.
14. **A part's file may hold only what `.dump` writes for that part:** its own tables and views, and `INSERT`s of plain values into its own tables. A trigger, another part's table, a query or an upsert in a file is refused with the file and line number.
15. **Each part reads only its own tables and the links README rule 6 allows.** SQLite's authorizer refuses any other read:
    - the room may read the materials products (and their text and units);
    - labour may read the materials products, units, lines and statuses, and the room's take-offs.

    Rule 5 stays a wall, as separate files make it today. Attached databases would separate the parts too, but SQLite can't enforce foreign keys across them.
16. **The layout is SQLite's.** The files must equal what `.dump` writes of the database loaded from them (load, dump, compare), which `mise run check` makes sure of. Within a table, `.dump` writes rows in the order they were added; meaning never depends on it, since order is `pos`.
17. **People read the data through views,** not through the raw files. Views in the schema follow the foreign keys to the names: `materials_show_line`, `room_show_item`, `labour_show_line` and `phases_show_step` (phases and steps numbered as printed). Comments in the files naming what keys point at were tried and taken out: they stored every name twice and brought the rename problem back into every diff.
18. **Changes are reviewed with `sqldiff`,** SQLite's own comparison tool, at two levels:
    - the tables, to see what was edited (exact and minimal: renaming a product is 1 row);
    - each version's views saved as tables, to see what it touches (every place the product's name now appears).

    `mise run diff` compares the data with the last published version both ways. Each side is built from its own commit's schema files, so a diff still works across a design migration.
19. **Messages name the file and tell things apart:** "MOYA wall-hung basin (item 4, Main wall)", "labour line 10 (…)". A message from the checks never shows a key. A message from SQLite itself while loading gives the file, line and rule.

## The design

The schema files in `etl/schema/` are the design; this section is a map of them. Load order: common, materials, room, labour, phases. In all, 91 tables, 25 check views and 4 reading views. The schema files also carry the meaning of each column, and the writing pattern for a product's name and detail: the comments that are in the TOML today.

- **common:** `common_language`, and the conventions every table follows (inside its `CREATE`).
- **materials:**
  - settings; section text and note;
  - labels and symbols;
  - units (with their measure and plurals), shops (with `sku_pattern`), work sections;
  - statuses (with their flags);
  - products (with their kind), with their text, where they're bought (`materials_product_shop`: shop and sku together) and assumed values;
  - lines (one per product, work section and status), with notes and who brings it.
- **room:**
  - the room's size; labels and symbols;
  - take-offs (codes, with their measure);
  - tiles;
  - surfaces: the floor and the 4 walls in order, then `room_wall` and `room_floor`;
  - the column (with `remark`: its figures were measured on site), the door and the lintel (one row each);
  - items, with a table per shape, their names, notes and assumed values;
  - norms (codes, with their source).
- **labour:**
  - settings; section text and note; labels and symbols;
  - Factor F (with `remark`: the VAT choice);
  - books (with `remark`: how to take in a new edition);
  - units (with their measure and plurals), work sections;
  - rates, with their text and assumed values;
  - lines, with their four sources, notes and assumed values.
- **phases:**
  - section text and note; labels and symbols;
  - phases; steps (within their phase);
  - the references in step texts and phase notes.

The links between parts are only the ones README rule 6 describes:
- the room → `materials_product` (tiles, door, lintel, items, and their kinds);
- labour → `materials_product` (counts, shares) and → `room_take_off` (take-offs).

## What SQLite enforces, and what stays in code

**The schema and its views enforce:**
- types (`STRICT`), required values, ids (16 hex digits), uniqueness, positions unique within their parent;
- every link (checked after loading, so a row may point at one loaded later), including references in text;
- one-row tables having their row, exactly 4 walls and 1 floor, at least one of each list;
- each item having exactly one shape, its shape allowed on its surface, a floor rect with no height;
- a product or its own name (not both), an item with a product not giving its own size;
- the door, lintel and tiles naming a product of their kind;
- the statuses' rules for price, shop and who brings it;
- a labour line having one source, each source measuring what its rate is priced by, and a count not mixing measures;
- a rate without a book being assumed;
- a kept book's rates giving a page, and other books' rates a url;
- every assumed value having its `how`.

**The loader and the code check** (shared code; items 7 to 12 are today's checks, moved unchanged):
1. Every translation table and every label follows its convention; no text is empty; every unit has its English plural.
2. Every assumed value is there.
3. Every gap in a text has its reference row, and every row its gap, in each language.
4. A part's file holds only what `.dump` writes for that part, and equals the dump.
5. English and Thai change together (in `save`, and against the last published data).
6. The vocabulary of labels, symbols, norms and take-offs equals the code's.
7. Thai and English carry the same `{…}` placeholders and the same numbers (`common.same_facts`).
8. Each text uses only its own placeholders, with no stray braces:
   - shop links: `{sku}`, `{sku_digits}`;
   - product details: their sizes and `{ip}`;
   - section notes: their own;
   - a book's item format: `{item}`;
   - room notes: none;
   - step texts and phase notes: their numbered gaps.
9. A shop's sku pattern is a valid pattern, and each product's sku matches its shop's.
10. The sizes the room needs from a product: a tile's `w`, `h` and `per_box`, square and in whole mm; the door's `w` and `h`; the lintel's `h`.
11. What each shape needs once its product's sizes are filled in.
12. A kept book's file exists.

## The migration (ETL), for the switch only

`etl/migrate.py` does three things:
- **Extract:** it reads the four TOML files after today's code has checked them, so nothing today's checks would refuse is migrated.
- **Transform:** it reshapes them into the design. Every difference between the TOML's shape and the design is in this one place:
  - old ids → keys, and every link with them;
  - the item table → a table per shape;
  - references in prose → numbered gaps and ref rows;
  - unit spellings → measures;
  - the room's slots → product kinds;
  - lines → ids and positions;
  - plurals, `times` and statuses moved to where they belong;
  - the notes and remarks that are only TOML comments today, carried by hand (`HOW`, `FACTOR_F_REMARK`, `BOOK_REMARK`, `COLUMN_REMARK`).
- **Load:** it puts the rows into a fresh database built from `etl/schema/` (the schema refuses anything that doesn't fit), writes each part's file with `sqlite3 .dump`, loads them again from nothing, checks the schema in them is the design, and runs every check.

Keys are worked out from the old ids (the first 16 hex digits of a SHA-256 of the kind and the id). So running the ETL again gives the same keys, and the files don't churn while the design changes. The exceptions are labour lines, whose keys come from their place in the list, and materials lines, whose keys include their status: moving a line in the TOML, or changing its status, gives it a new key on the next run. The ETL is rerun until the design is right, then once more at the switch. After that it's retired and kept only in git history.

**Proof, on today's data** (run on 2 November 2026):
- `migrate.py`: 91 tables, 1,272 rows, 0 problems, the schema in the files equal to the design, and the round trip (load, `.dump`) identical.
- `fidelity.py`: each TOML file rebuilt from the database, 0 differences. Labels, symbols and assumed keys are compared as sets, since they have no order. Every table not filled from the TOML is accounted for (the languages, the statuses, the take-offs, a share line's own row). Integers stored as reals (`3000` read back as `3000.0`) compare equal, which is harmless because the code prints numbers with `:g` and `money()`.
- `prove.py`, 85 of 85 as they should be:
  - 61 database breaks, each refused by its intended rule;
  - 9 broken part files (a trigger, another part's table, a query, an upsert, a value too many …), each refused;
  - an edit inserting a step between two others adds 3 lines and changes none, and the same step in Thai only is refused with the files untouched;
  - English changed without its Thai is caught, for a product and for a label;
  - 6 reads, each allowed or refused by the authorizer as rule 6 says;
  - the working database's guards: `status` sees an unsaved change, `load` won't overwrite it, `save` won't write English changed alone, `save` writes both changed together.
- SQLite's own command-line tool loads the files with none of our code: integrity check ok, 0 broken links.

**The 12 "how" notes:** three rows come from TOML comments (the heater's IP rating; the shower head's x and y). The other nine are new and need the owner's check: the floor's two falls, the shower zone's waterproofing, the disposal rate, the old wall's area, the old tiles, and the three pipe runs.

## After the switch: changing the design

A design change is a numbered step in `migrations/`:
- the new schema;
- and, where a plain copy isn't enough, the step's SQL (splitting a column, filling a new one).

`mise run migrate` then:
1. loads today's data under the current schema;
2. builds a fresh database from the new schema;
3. copies every row across by table and column name;
4. runs the step's SQL and every check;
5. writes each part's file with `.dump`.

Nothing is written if a check fails. The part files record the step they're at, and a test replays the steps from step 0 (the ETL's output) and compares the result with the files.

Ready-made migration tools were tried on this schema on 2 November 2026; none fits:

| Tool | Version, released | Result |
|---|---|---|
| sqldef | 3.11.29, 30 Oct 2026 | its parser fails on `GLOB` in the first table |
| Atlas | 1.3.0, 29 Jul 2026 | "views are available to logged-in users only" |
| dbmate | 2.37.0, 18 Oct 2026 | changing a rule failed: SQLite won't rebuild a table a view uses (rolled back safely) |
| goose | 3.29.0, 11 Oct 2026 | same as dbmate |
| sqlite-utils `transform` | 4.2.1, 13 Aug 2026 | rebuilds columns safely, but not a changed rule |
| Alembic | 1.20.1, 22 Oct 2026 | needs SQLAlchemy models, a second copy of the schema |
| yoyo | 9.0.0, Aug 2024 | no release in two years |

All of them alter a long-lived database in place. Ours is rebuilt from text every time, so building the new design fresh and copying the data across is simpler and can't hit the view problem. That's a few dozen lines of our own; it's the least-worst option.

## Tools

- **`sqlite-tools` 3.54.1** (16 Oct 2026), from sqlite.org's own download: `sqlite3` (which dumps and loads the part files), `sqldiff` and `sqlite3_analyzer`. It's pinned in `mise.toml` per platform (`http:sqlite-tools`):
  - Linux x64, used here and by GitHub, is tested;
  - macOS on Apple silicon and on Intel are listed, and their downloads exist;
  - there is no download for Linux on ARM (a Linux VM on an Apple-silicon Mac).
- **The build** uses Python's own `sqlite3` module (SQLite 3.53.1 in the pinned Python 3.13.18) to load the part files and run the checks. `.dump` itself comes from the pinned `sqlite3` tool, so it's the same everywhere. No new Python package is needed.

## Tests after the switch

- Each test copies the loaded real database (SQLite's `backup`, well under a millisecond) and breaks it with plain SQL. It expects the refusal of the rule it breaks, worked out from the real data (rule 9). It finds what it breaks by what it is ("an item with a product on a wall", "the first phase"), never by today's names, numbers, positions or rows, as `etl/prove.py` does.
- Tests of the loader break copies of the part files.
- Tests of changes go through `load`, `sql` and `save`, including their guards.
- `test_pipeline.py` today edits TOML through `data(lambda d: …)` in 88 places, and every one is rewritten. The expectations stay; only how each test breaks the data changes.

## The switch, as one change

1. Run the ETL one last time, and commit its part files at the top of the repo (`common.sql`, `materials.sql`, `room.sql`, `labour.sql`, `phases.sql`). From then on the schema lives in them, and `etl/schema/` goes. Add `*.db` to `.gitignore`.
2. Move the shared database code from `etl/` into `common.py`: `load`, `dump`, the checks, `names`, `reading` and `changed_alone`. Move `edit.py`'s commands to the top of the repo.
3. Rewrite the four parts' loaders to read the database (each through its own `reading` limit), not the TOML, into the same objects as today. Rendering, the room's geometry, the design checks and the drawings are unchanged, except that references in the phases come from rows.
4. Remove what the schema now enforces from the code: `common.check`, the field declarations, the hand checks listed above as moving, and `STATUS`. The code reads the statuses' flags. Keep the checks under "The loader and the code check".
5. `build.py` builds the database once, hands each part what it needs, and passes the room and the materials list along as today (rule 6).
6. `mise.toml`:
   - add `load`, `save`, `status`, `sql`, `show`, `diff` and `migrate`;
   - `publish` refuses unless `status` says `quote.db` holds nothing unsaved;
   - `check` gains the dump comparison and the English and Thai check against `origin/main`;
   - `materials` and `phases` (which print a part on its own) build the database first;
   - `sqlite-tools` is already pinned (done with this plan).

   `pages.yml`: `fetch-depth: 0`.
7. Rewrite `test_pipeline.py` as above.
8. Rewrite the README:
   - the Files table, How the quote is made, the Glossary (which names `phases.toml` and `materials.toml`) and Commands;
   - rule 1 (the part files and the working database);
   - rule 2 (consistency is the schema plus the dump layout; ids are random keys, not names that say what they are);
   - rule 3 (names as translation tables; English and Thai change together);
   - rules 5–7 (data file now means a part's `.sql` file; keys and codes; the authorizer; codes held in code and data, kept equal);
   - rule 8 (messages name the file and the thing);
   - rule 9 (tests copy the database);
   - rule 10 (assumed values with `how`; the rate book's note on a new edition is its `remark`, not a comment in `labour.toml`);
   - Checks (which checks are the schema's and which the code's; the check against the last published data is a check on a change, alongside data and design checks).
9. Delete the TOML and `etl/`.
10. **Prove it:**
    - `out/index.html` is byte-identical to today's, except where the page says "generated from room.toml" (it then names the data file);
    - the PDF's text (`pdftotext`) is identical apart from that;
    - `mise run ci` is clean, with 0 design problems;
    - each new check is shown to fail when broken;
    - an independent review;
    - the GitHub build is green.

## Open

- **Rules that overlap the room's design checks:** a shape's `x >= 0` and `y >= 0` make a negative position a data error, where today the room design check reports an item off its wall. A negative position can't be meant, so it stays a data error.
